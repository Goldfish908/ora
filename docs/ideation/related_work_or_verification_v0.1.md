# 竞品精读：ICML 2026 OR 建模验证类四篇 v0.1

日期：2026-11-17
范围：VeriSimpl、Opt-Verifier、Draft-and-Audit RL（DA-RL）、ORLoopBench 的全文精读，以及它们与"可进化的分层验证经验"方向的差异。
说明：[Lxxx] 为全文抽取文件中的行号；标注"推算"的数字是根据论文百分比反推的，论文本身未给出。

---

## 0. 结论

1. **"能执行不等于正确"已经不是新问题。** 四篇都把它当作动机：DA-RL 称为 silent modeling failure，ORLoopBench 称为 semantic drift，VeriSimpl 和 Opt-Verifier 写在引言第一段。这一点只能作为背景。
2. **四篇的"正确"都止步于目标值匹配。** 没有一篇用独立于目标值的语义检查来判定正确性。我们的幻影（目标值对、语义错，RetailOpt 上 32% 目标匹配 vs 6.8% 真正确）在它们的指标下全部算作正确。这是我们最硬的差异点。
3. **四篇都不积累验证知识。** 每题从零开始：VeriSimpl 和 Opt-Verifier 靠 prompt 现场验证，DA-RL 用固定 rubric，ORLoopBench 靠求解器的 IIS。跨任务积累、带出处、可迁移的可执行检查，在这条线上是空白。
4. **四篇都处理不了"题面没写的惯例"（C 类）。** VeriSimpl 自己承认只能检查程序中已有的约束，遗漏的方面无法探测 [L250]；Opt-Verifier 的"隐式约束"指的是教科书题型的标准结构；DA-RL 的 rubric 没有这一项；ORLoopBench 的错误全是人工注入的显式错误。
5. **四篇都没有同时报告可执行率和正确率，也没有统计"修复把对的改错"。** ORLoopBench 的 semantic drift（GPT-5.4：90% 可解但只有 28.2% 目标值正确 [L315]）是唯一接近我们洗白发现的数据，但它只在一个 4 行表格里出现，而且检测仍然只靠目标值。
6. **我们的定位**：它们验证的是"程序和题面是否一致"或"目标值是否对"；我们验证的是"解是否符合问题语义，包括没写明的惯例"，并且把验证知识跨任务积累下来，同时保证修复不会把错误洗白。

## 1. 逐篇要点

### 1.1 VeriSimpl（ICML 2026）

- **方法**：采样 K 个候选程序（最多 10 个），每个先经过报错驱动的修复，使其可执行 [L59]，然后用求解器构造简化的诊断问题，让同一个 LLM 只根据题面判断：
  - 约束检查：把每条约束改成三种变体（收紧、取等、反向），让求解器找满足条件的解，再问 LLM 这个解是否可行。prompt 会让 LLM 写一段 Python 可行性检查程序，涵盖"显式和隐式约束"。这实际上就是**每题现场生成的可执行检查**，和我们自动写的检查非常接近。
  - 单变量检查：遮住一个变量，让 LLM 推算它的值，要求和求解器完全一致。
  - 全变量检查：相当于让 LLM 把整题解一遍。
  - 三项分数等权相加，选最高的候选。验证只用于**选择**，不触发修复，也不拒答。
- **验证质量**：只有"全部检查通过"这一信号的精度和覆盖率。GPT-4o 平均精度 91.5、覆盖率 34.2；R1 为 78.5 / 23.0。没有单项检查的误报率，没有修复导致的回退统计。
- **结果**：GPT-4o 平均准确率从 56.6（BaseLLM）提高到 65.5；R1 从 62.5 提高到 72.8。数据集为 NL4Opt 269、NLP4LP 62、ComplexOR 17、IndustryOR 96。
- **弱点**：
  - 基线计算量不对等：VeriSimpl 用 K=10 加验证，对比的是单样本基线，没有多数投票或 best-of-K 基线。
  - 准确率没有定义，应该就是目标值匹配；文中多处数字前后不一致。
  - 作者承认的失败模式就是我们的幻影：变量含义理解错（"start time"）、利润漏算原材料成本，程序内部自洽，验证照样通过 [L250, L798]。
- **和我们的关系**：最直接的竞品。它的"按约束变体生成探测解"可以借来当我们 L1/L2 检查的探测手段。

### 1.2 Opt-Verifier（ICML 2026，中科大与华为诺亚）

- **方法**：全部由 LLM agent（GPT-4o-mini）完成：
  - 结构侧：把模型回译成三层结构（问题类别、变体、具体约束），再和从题面提炼出的结构对齐。
  - 解侧：用自然语言解释求解结果，让 LLM 判断是否合理、是否最优。
  - 只修正一轮 [L403]。每题约 9 次调用、5k–8k token。
- **验证质量**：构造的测试集是 30 个正确模型加 270 个人工破坏的模型，报告的是负类的精度和召回。按论文自己的数字反推，正确模型被误判为错的比例很高：结构侧 Easy 约 67%，Hard 档推出来的误报数甚至超过正样本总数。要么样本量写错，要么验证器拒掉了大部分正确模型。这和我们 D1 的 49% 误报属于同一类问题，只是它没有报告。
- **结果**：五个数据集的平均从 32.7（Standard）提高到 64.3；IndustryOR 45.0，o1 为 36.0。摘要说"提升 20% 以上"，正文又说约 10%，三处口径不一致。
- **弱点**：验证器和生成器是同类模型；"最优性"由 LLM 判断，没有依据；没有可执行率；修正是否把对的改错没有统计；fine-tuned 基线的数字是从不同版本数据集抄来的。
- **和我们的关系**：适合作为"由 LLM 判断语义"的基线或消融，用来和我们有出处依据的检查做对比。

### 1.3 Draft-and-Audit RL（ICML 2026，阿里）

- **方法**：Qwen2.5-7B-Instruct，同一个模型先写 PySCIPOpt 草稿，再按固定 rubric 审查（约束是否一致或遗漏、参数是否和题面一致、变量类型是否正确）。只执行最终程序，奖励为目标值匹配（容差 1e-6）。用的是 PPO（每题一条 rollout、无 baseline、无 KL），不是 GRPO。
- **静默错误**：定义为"程序能跑、给出一个看似合理但错误的数" [L87]，完全以目标值为准。头条结果"MAMO-Complex 上静默错误从 32.6% 降到 0.0%" [L307]：
  - 推算样本量约 43：14 个静默错误中，6 个修好，8 个变成了执行失败（论文归因为"格式漂移"）。所以头条结果主要是**静默错误变成了崩溃**，而不是变成了正确。
  - "0% 回退"大约是 29 个中 0 个（MAMO-Complex）和 6 个中 0 个（OptMATH）。
- **结果**：五个 benchmark 的宏平均 68.1。对照：Claude Sonnet 4.5 67.1、Opus 4.5 67.0、SIRL-7B 60.6。IndustryOR 只有 36.7。训练和测试来自同一个 benchmark 的 80/20 划分，IndustryOR 测试集只有 20 题，一题就是 5 个百分点。
- **附录里的证据**：六个"实质修正"例子中有四个是 TSP。草稿没有消除子回路，审查只删掉了打印代码，于是程序从崩溃变成能跑但答案错误。这正是我们说的洗白。
- **和我们的关系**：RL 路线最接近的工作。它的奖励直接奖励幻影，可以设计"目标值奖励 vs 经 witness 把关的奖励"的对照实验，把它的局限变成我们的贡献。

### 1.4 ORLoopBench（ICML 2026）

- **方法**：给定一个人工注入错误、已不可行的 LP/MILP 模型，agent 根据 Gurobi 的 IIS 迭代修复。共 9 类注入错误；LP 规模很小（平均约 10 条约束、8 个变量）。Qwen3-8B 经 SFT 加 GRPO（LoRA）后，LP 修复成功率 95.3%，Claude Sonnet 4.6 为 92.4%。
- **成功标准**：恢复到可解，且目标值和原模型相差在 5% 以内。奖励函数里**没有**保持目标值或防止语义漂移的项，和贡献声明不符。训练时的工具反馈部分是模拟的，按概率返回可解。
- **Semantic drift**：整体重写模型时，GPT-5.4 有 90% 可解，但只有 28.2% 目标值正确 [L315]。实例数量、prompt 和协议都没有给出，检测只看目标值。作者明确说"可行但错误的模型需要外部参考或规格测试，本文只略有涉及" [L2128]。
- **和我们的关系**：可以引用为独立证据，说明修复和重写压力会把可见的失败变成看不见的错误。它的范围到可解为止，而我们的问题恰好从可解开始。它说需要但没有做的"外部规格测试"，就是我们的 L1/L2 检查。

## 3. 共同盲区，也就是我们的机会

1. **目标值匹配下的幻影。** 四篇的指标都看不见。我们有 RetailOpt 的 witness 作为独立的真值，这是独有的资产。
2. **题面没写的惯例（C 类）。** 没有一篇把它当作独立的问题，更没有限定适用范围的机制。
3. **验证知识的积累和迁移。** 四篇都是单题内验证。记忆类工作（ProcMEM、UMEM 等）存的是技能，不是检查，而且不做 OR。
4. **可执行与正确之间的冲突。** DA-RL 的数据里两个方向都出现了（静默变崩溃、崩溃变静默），ORLoopBench 有 semantic drift，但没有人把它当作机制问题来处理。我们的"低层修复不得破坏高层检查"规则正好回应这一点。
5. **验证器的误报。** Opt-Verifier 的隐含误报率很高，VeriSimpl 只用作软分数、回避了这个问题，DA-RL 的 rubric 每次都会整段重写代码。"没有出处的检查不能否决"有现成的反面证据可以引用。

## 4. 定位

**主张**：OR 建模里的验证，不能只在单题内用 LLM 判断，也不能只看目标值。可靠的做法是把验证知识沉淀为带出处、可执行、分层的检查；这些检查只有验证通过后才能晋升，跨任务积累，并且约束修复不得破坏高层语义。

**避免的说法**：
- 不说"我们首次发现能执行不等于正确"。
- 不说"我们首次提出 OR 建模的验证"。
- 不用目标值准确率作为唯一的主指标，否则就落入和四篇相同的口径。

**必须做的基线**：
- VeriSimpl：改成 PySCIPOpt 复现，再加一个计算量对等的 best-of-K 基线。
- Opt-Verifier：按附录 prompt 复现，单轮。
- DA-RL：先复现推理端的 Draft→Audit prompt；如果做 RL，再用我们的 GRPO 设置复现它的训练。
- ORLoopBench 不当基线，作为引用和对照证据。

## 5. 由此引出的实验

1. **用 witness 重新评判竞品的输出**（不需要训练）：在 RetailOpt 上运行 VeriSimpl、Opt-Verifier 和 Draft→Audit，分别报告可执行率、目标值匹配率、witness 判定的真正确率、幻影率，以及修复前后对错翻转的数量。预期：三者都能提高目标值匹配，但真正确率提升有限，幻影数可能增加。这个实验直接证明"它们的指标高估了正确性"。
2. **奖励对照**：目标值奖励 vs 经 witness 把关的奖励，比较训练后的幻影率。
3. **竞品验证器的误报率**：在 witness 判为正确的模型上，统计 VeriSimpl 和 Opt-Verifier 验证器的误报率，与我们按出处设门槛后的检查对比。
4. **借用 VeriSimpl 的探测方法**：用约束变体生成的探测解，作为我们 L1/L2 检查的输入，可以提高召回。

## 6. 风险

- **RetailOpt 只有一个领域。** 如果幻影只在 RetailOpt 上大量出现，审稿人会认为这是 benchmark 的特性。必须在至少一到两个其他数据集上找到同类现象，比如在 IndustryOR 或 OptMATH 上人工审计一部分题目。
- **约 54% 的 RetailOpt 幻影只违反了 C-INIT。** 也就是说，有相当一部分可以算作"题面没写清楚"，而不是模型错了。论文必须正面处理这个问题：把 C 类单独作为研究对象，而不是全部算成模型错误。
- **复现成本**：三个竞品都依赖 Gurobi 或特定 prompt，移植到 PySCIPOpt 需要说明改动。
- **记忆类工作还没精读**：ProcMEM、UMEM、MemEvolve、XSkill 只看了摘要，需要补读，以确认"验证知识积累"在 agent 记忆方向上同样是空白。
