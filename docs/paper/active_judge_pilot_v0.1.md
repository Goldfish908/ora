## 1. 要解决的问题

静态摘要版判官的跨族失效(dev70 检出 60.9% → F5–F8 检出 14.7%),根因诊断:
**训练带来的提升全部来自"学会读摘要里的幻影信号",摘要覆盖不到的地方,训练和没训练一样盲。**
F5–F8 漏检细胞 83%(24/29)是 C-DEMAND(需求履约)类违例,其证据不在 F1–F4 时代设计的解摘要字段里。

## 2. 架构:判官从"读固定摘要"升级为"主动写检查"

```
[题面 + 数据摘要 + 模型代码 + 解摘要]
        │
        ▼  ①规划(判官 LLM):枚举题面声明的每条要求,写出检查脚本
Python 检查脚本(读 solution.json + data.json)
        │
        ▼  ②沙箱确定性执行(本地,timeout 30s;崩溃自动修复一轮)
CHECK <name>: PASS/FAIL <数字证据>
        │
        ▼  ③判决(判官 LLM):区分 (a)脚本故障/(b)前提不匹配/(c)真实违例
VERDICT: VALID / INVALID(fail-open:存疑一律放行)
```

关键设计:
- **感知由判官自己驱动**:检查什么由模型按题面决定,不再受预设摘要字段限制;
- **执行是确定性的**:证据来自真实计算,不是模型想象;
- **判决三分法**(故障/前提错配/真实违例)是对治"检查脚本本身的 bug"的核心机制。

## 5. v4 残留失败的结构分析(指导判官 v4 训练数据设计)

19 个漏检细胞的归因:
- **13 个:检查脚本已写出 FAIL,但判决器驳回**——多数是"前提错配"类驳回:判官写的需求检查是朴素的"sales == demand",而 RetailOpt 允许销售损失(带罚),同一检查在正确解上也会 FAIL,判决器因此学会驳回它。**真正的业务物理更微妙:"有库存却丢了销售"才是违例**——这正是蒸馏训练(路径③)该教的东西:不是"查需求",而是"查有库存下的丢单"。
- 6 个:规划器压根没写需求类检查(覆盖缺口)——蒸馏时应加入"枚举题面每条声明要求"的程序化行为。

按家族看检出率的偏斜:f7(转运/网络结构)71%(10/14),f5(库存/服务
陷阱)25%(2/8),f8(门店发货/可持续/逆向物流)27%(3/11),f6 0/1。
f7 的检查(流量守恒类)是可写谓词的典型,f5/f8 的陷阱则更依赖
"业务惯例知识"(如服务水平的口径),这正是零样本判官的薄弱处。

纪律声明:v4 之后不再在 F5–F8 上迭代提示词(已过拟合风险边界),IndustryOR 是唯一未触碰的终验集合。

规则(检出+误报双指标)正是为此而设。

### 6.1 判官 v3 在 IndustryOR 上的误报机制(22 个 FP 细胞解剖)

v3 的 22 个误报与零样本直判的 4 个误报**零重叠**——蒸馏没有继承直判的
失误,而是制造了全新失败模式。FP 在变异臂(z0/z1/z2 = 5/8/9)与难度
(Easy/Medium/Hard = 5/9/8)上均匀散布,不是内容相关的个别误判,而是
系统性偏移。抽读 FP 判决词,机制一致:**凭空指控**——对合法解提出
听起来专业但实则不成立的语义异议,例如:
- 把题面允许的连续工时解读成"应按整天取整",指控解"允许分数工日";
- 自行发明课程先修组合约束,宣称已验证可行的选课方案"不可行";
- 声称目标函数"装配了错误的量",但引用的对照式是自己臆造的。

即:**蒸馏把"保持怀疑"迁移过来了,却没把"如何验证怀疑"迁移过来。**
v3 在 F1–F4 上学到的幻影信号与摘要字段强绑定,到了没有这些字段的
IndustryOR,怀疑的阈值已被调低,验证的手段却缺席——判决退化为
语义层面的臆造违规(confabulated violations)。这正是 v4 改用
judge-writes-checks 形态的根据:检查脚本必须在沙箱里对真实数据
执行,判决被锚定在可复算的证据上,臆造在结构上无法产生 FAIL 信号。

对照组(F5–F8 上的同一并集分析):主动 v4、零样本直判、静态 v3 三通道
并集检出 16/34 = 47.1%,仅比主动 v4 单通道(44.1%)高 3 个百分点
(主动∩直判重叠 6 例,直判独有仅 1 例),并集误报不增(7.1%,唯一
FP 细胞仅主动 v4 触发)。两个集合对照读:族内迭代后主动判官在
F5–F8 上几乎吸收了其它通道的视野,多通道集成收益有限;而在未见域
(IndustryOR)通道间互补性显著(+8.2pp)——**集成的价值与域陌生度
正相关**,这支持"单通道参数化迁移 + 陌生域多通道裁决"的分层终局形态。

### 结论(诚实版)

1. **F5–F8 上的 44.1% 有相当部分来自 4 轮族内迭代**(v1 零迭代只有 8.8%)。
   零迭代条件下,主动架构在未见域(IndustryOR)不超零样本直判基线——
   "judge-writes-checks" 的架构优势不是免费的,瓶颈在**检查规划**:
   判官不知道这个新域该查什么。
2. 这精确界定了参数化的任务:判官 v4 蒸馏要教的不是"RetailOpt 的规则",
   而是"面对新域,从题面枚举可判定谓词"的程序性技能——
   F5–F8 迭代史(v1→v4)恰好提供了这种程序的种子轨迹。
3. 误报控制是主动架构的真实优势:0.0%(插桩)vs 2.2%(直判),且沙箱执行给了判决可审计的证据链。
4. 互补性(并集 39.3%)提示终局形态可能是多感知通道的裁决集成,而非单一判官。

## 8. wrong_constant 失败模式专析(采集中途,79 细胞)

错常数变异的漏检结构与其他类根本不同:判官写了 14 个检查(库存平衡/
容量/销售可用性/MOQ……)**全部 PASS**——因为变异模型的解天然满足它自己
的(错误)约束。唯一可能抓到它的检查类型是**代码-数据常数对账**:把
gen.py 里的数字字面量逐个与 data.json 真值核对,而规划器几乎从不自发写
这类检查(它面向"解的物理性",不面向"代码的保真度")。

两条对策:
1. v4 数据层面:wrong_constant 细胞拒绝采样留存率天然偏低(~48%),v4.1
   应考虑对该类过采样,或在规划器课程中加入常数对账示范。
2. 系统层面:常数对账其实是**确定性可解的**——AST 提取代码数字字面量,
   与 data.json 模糊匹配,不匹配的报出。这更适合做成 harness 的确定性
   探针(pre-solve 层),而非占用判官的推理预算。与 E 线 pre-solve 闸门
   汇合。

## 9. 常数审计探针(p17):wrong_constant 的确定性解法

第 8 节假设的确定性探针已实现并验证(scripts/p17_const_audit.py,纯 AST+
数据扫描,零 LLM)。发现变异有两种形态,需要两个互补通道:

1. **直接替换型**(真常数被改成相近字面值):近似失配通道——代码字面量的
   最近数据值相对差落在 [7%,31%] 区间(10–30% 偏移的签名;合法容差/big-M
   离任何数据值都很远)。
2. **乘性因子注入型**(`1.25 * costs['inventory'][p]`,字面量本身无真值可
   对):因子通道——AST 找"常数×数据引用"且常数在 [1.08,1.45]∪倒数带。

**效果**(judge_v2 全部 762 细胞):
- wrong_constant:检出 **140/140 = 100%**,正确代码误报 **2/103 = 1.9%**
- 特异性:对 phantom_inventory(1.5%)/drop_constraint(0.6%)几乎不触发
  ——通道各管各的病
- 因子通道单独:99.3% 检出 / **0% 误报**

这给出一条架构原则:**能确定性判定的语义,就不该占用 LLM 推理预算**。
判官的分工由此清晰:确定性探针管"常数保真"(代码↔数据),
judge-writes-checks 管"解的物理合法性"(解↔题面),witness 管终审。

### 9.1 探针跨域验证(IndustryOR,冻结参数零调优)

把 p17(参数在 RetailOpt 上定)原样跑在 IndustryOR 240 细胞(数据常数从
题面文本正则提取代替 data.json):错误细胞触发率 4.8%–8.3%,正确细胞
0%–1.6%。结论:IndustryOR 的语义变异几乎不是常数篡改(是结构性/语义性
错误),探针在该域**无害(误报≈0)但无覆盖**——它管 RetailOpt 的
wrong_constant,IndustryOR 的病要靠 judge-writes-checks 通道。
各感知通道的适用域由此划清,且常数探针可以默认常开(误报代价≈0)。

### 9.2 探针在 F5–F8 留出族上的覆盖(p21,48 细胞)

把同一探针(冻结参数)跑在 F5–F8 终测集上(scripts/p21_const_audit_f5f8.py;
代码从评测提示词的 [MODEL CODE] 段提取,数据来自冻结制品 data.json):

| 通道 | 检出(34 错) | 误报(14 对) |
|---|---|---|
| 常数审计(波段 7%–31%) | **0/34 = 0%** | 0/14 = 0% |
| 常数审计(放宽到 3%–60%,敏感性) | 4/34 = 11.8% | 2/14 = 14.3%(超阈) |
| 主动判官 v4 零样本 | 15/34 = 44.1% | 1/14 = 7.1% |
| 并集 | 44.1%(+0) | 7.1%(+0) |

结论:F5–F8 的真实轨迹错误**几乎不含常数篡改**——幻影初始库存、多梯队
流量守恒这类错误是"少了一条约束"的结构缺失,代码里没有一个字面值是错的,
探针无从触发。放宽波段的边际检出以误报超阈为代价,不值。这与 §9.1 的
IndustryOR 结果共同把图景补全:**三个域、两种错误机制——F1–F4 工厂变异
以常数篡改为主(探针主场),F5–F8 与 IndustryOR 以结构/语义缺失为主
(judge-writes-checks 主场)。** 探针零检出不是探针失效,而是错误机制
分布随域迁移的又一独立证据;常开它仍是对的(误报≈0,撞见常数病就是
白捡)。

## 10. 检查词汇表分析:跨域时判官"查什么"的塌缩

对三类集合中成功检出(TP)细胞,统计判官写出的检查名频次:

- **F1–F4(训练分布内)**:业务语义检查为主——moq / sales_availability /
  init_nonfresh_inv / demand_fulfillment / aging_balance……
- **F5–F8(RetailOpt 宇宙内跨族)**:同一词汇表成功迁移——语义检查仍在
  唱主角(这正是族内迭代后 44.1% 的来源)。
- **IndustryOR(未见域)**:检查词汇塌缩为**通用求解器健全性**——
  status_optimal / objective_match / integrality / non_negativity。
  抓到的错误几乎都靠 objective_match/integrality,业务语义检查缺席。

这把"规划覆盖缺口"从计数层面落到机制层面:**零样本面对新域时,判官的
规划器退化为通用代码审查,不再构造业务谓词。** v4 蒸馏的目标因此更精确:
不是教" RetailOpt 的 moq 检查",而是教"从题面枚举业务声明→落成可执行
谓词"的程序。训练信号是否足以教会这一程序,由 v4 在 IndustryOR 上的
终验回答。

3. **F2 误报 13.0% 超阈**:采集池整体误报 5.9% 达标,但 F2(多周期库龄

## 13. 误报机制分析(15 个 FP 细胞,采集池全量)

逐细胞解剖 15 个误报(正确解被判 INVALID),触发的失败检查分布:
objective/objective_consistency 10 次、demand_fulfillment 7 次、aging/waste
balance 各 3 次。归为两类机制:

1. **判官断言过强**(demand_fulfillment 类):判官自发写的检查假设"需求
   必须 100% 满足",但题面允许 lost sales——检查本身编码了错误业务假设,
   正确解自然"违规"。
2. **判官目标函数想象偏差**(objective_consistency 类):判官按自己理解的
   目标结构重算目标值,与求解器报值对不上——在价格档/蚕食等目标结构
   复杂的变体上(F2 族,9/15 误报集中于此)尤其明显。

关键性质:**这 15 个细胞因判决与真值不符,已被拒绝采样整体剔除**,其
规划器/判决器轨迹均不进入 v4 训练数据。因此蒸馏不会放大误报;v4 在
F5–F8 上的误报率应 ≤ 零样本主动判官的 7.1%——待 v4 评测验证。

## 14. v4 终验判定规则(预注册,2026-11-08,先于任何 v4 结果)

为避免事后移动球门,在 v4 训练/评测完成前固定判定逻辑:

**F5–F8(48 细胞,族内迭代集,只作参考不作判据)**:蒸馏后检出率
相对零样本主动判官(44.1%/FP 7.1%)不应显著退化;误报 ≤10%。

**IndustryOR(240 细胞,零迭代终验集,核心判据)**:将 v4 与四条
已冻结基线对比——零样本直判 31.1%/FP 2.2%、主动·重推导 23.0%/3.9%、
主动·插桩 19.7%/0.0%、训练判官 v3(静态摘要)24.6%/12.3%(误报超阈)。

口径说明:v4 臂实际需要插桩沙箱制品(ior_sandbox),3 个细胞因插桩
求解未产出 solution.json 而缺制品,故 v4 臂 n=237(60 错 / 177 对),
缺额 z0_1(错)、z1_36(对)、z2_36(对)。各臂按自身集合计率,
对照时以率(非计数)为准。

判定分三档:
- **达标**:v4 检出率 ≥ 零样本直判(31.1%)且误报 ≤10% → 蒸馏把
  "从题面枚举业务声明→落成可执行谓词"的程序迁移到了未见域,
  跨族失效问题在参数化路径上被解决,goal 判 complete。
- **部分达标**:v4 超过插桩形态(19.7%)但未达 31.1% → 参数化有效
  但不充分,结论写为"蒸馏保留了族内能力、未见域迁移有限",
  后续走检查器作者化/多通道集成(两臂并集已示 39.3% 潜力)。
- **未达标**:v4 ≤ 19.7% 或误报 >10% → 如实报告蒸馏未能迁移检查
  构造程序,给出失败归因(数据规模/纯度上限 68.5%/域差距)与
  下一步,goal 按证据结题。

无论哪档,F5–F8 上的架构有效性结论(44.1% vs 14.7%/20.6%)不受影响——
它已在零样本提示词层面成立;IndustryOR 检验的是参数化后的迁移保持度。

## 15. 附录:主动判官工作机制的两个完整实例(F5–F8,零样本 v4 提示词)

**例 1:retail_f5_storage_overflow_v0(真实标签:错)→ 判官检出 ✓**

判官规划器一次性写出 11 项检查(脚本 11.7K 字符),沙箱确定性执行结果:

```
CHECK initial_inventory: FAIL init_nonfresh_total=2.500000, init_nonfresh_count=5
CHECK storage_capacity: PASS   CHECK production_capacity: PASS
CHECK sales_availability: PASS CHECK waste_equation: PASS
CHECK aging_equation: PASS     CHECK fresh_inflow: PASS
CHECK moq: PASS                CHECK non_negativity: PASS
CHECK lost_sales_nonneg: PASS
CHECK objective_consistency: PASS reported=1428605.00, computed=1428130.00
```

判决器推理(节选):"inventory appearing from nowhere in the non-fresh
buckets at period 1 … violates the zero-initial-inventory convention"→
VERDICT: INVALID。注意幻影库存量仅 2.5 单位——目标值几乎无扰动,
纯执行信号(目标值对账)结构性看不见,只有语义检查能抓到。

**例 2:retail_f7_transshipment_v2(真实标签:错)→ 判官检出 ✓,且展示判决三分法**

沙箱执行报出两个 FAIL:

```
CHECK init_nonfresh_inv: FAIL 48 entries with total 7053.00 non-fresh inventory at t=1
CHECK objective: FAIL computed=269720.00 vs reported=319382.00 (缺 holding 成本项)
```

判决器对两个 FAIL 做了不同处置:对 objective FAIL,它识别出"脚本未计入
holding 成本,比较无效"——归为**脚本故障**,不予采信;对 init_nonfresh_inv
FAIL,它引用题面("期初零库存 + 零提前期,t=1 订单只能产生新鲜库存")
判定为**真实违例** → VERDICT: INVALID。一次判决中同时演示了"驳回脚本
bug"与"采信真实违例",这正是判决三分法(故障/前提错配/真实违例)
设计的意图:检查脚本可以有 bug,但 bug 不自动等于被审解有罪。
