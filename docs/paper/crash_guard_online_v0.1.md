# Crash Guard 在线对照实验 v0.1(B' 臂：guard + 预求解闸门）

日期：2026-11-02（全量收官：B' 臂 309 条记录，177 个 loop 细胞全部终局）。

## 1. 实验设计

- **臂 B'**:`scripts/m1_presolve_loop.py` + crash guard v0.1(G0–G5，
  `--guard-turns 1`，检出→针对性修复提示→LLM 重写一次，不求解）+
  预求解闸门（同 B 臂）。5 分片并行，on 模式，max 3 轮。
- **对照**：B 臂（仅闸门，无 guard,F14 已收官）；两臂共享 round-1 pilot。

### 5.1 部分数据的方法学警示（2026-11-02 中期检查，~66% 记录）

在中期快照（B' ~212/322 条记录）上直接跑主分析会产生**系统性低估
B'** 的假象：B' 正在进行的细胞只写入了部分轮次记录，分析脚本按最新
已完成轮次计终局，使在途细胞（多为打满 3 轮的难细胞）被记为失败；
而对照 B 臂早已全量完成。表现为配对翻转 B-only 19 / B'-only 8、
crash 47 vs 37——与 §5 完全配对快照方向相反。结论：**配对比较只对
两臂均已收官的细胞有效，部分数据快照不可用于决策**；最终结论以全量
完成后重跑的 `psv_online_analysis.py` 主表为准。

## 6. 结论

**假说成立。** B 臂 crash 残余膨胀（18→37）确由闸门反馈重写引入的新
API 错误所致：B' 臂（guard v0.1）将 crash 残余从 37 压回 **19**，与无
闸门 A 臂的 18 基本持平，即 guard 几乎完全抵消了闸门重写带来的 crash
副作用。

定量结论：

1. **crash 残余 37→19(−49%)**，同时真成功率 87→90(45.8%→47.4%),
   配对净翻转 +3。guard 不仅防崩，还把省下的轮次转化为真实成功。
2. **失败层级整体上移**:crash 减少的 18 例几乎全部转化为
   witness_infeasible(+20)——代码从"跑不起来"变成"跑得起来但语义不
   满足出题人意图"。崩溃层问题已被 guard 显著压缩，**主要矛盾转移到语
   义层**（witness_infeasible 70 例，占残余的 70%)，这正是蒸馏/语义
   层约定的用武之地。
3. **错误级联真实存在但有限**:guard v0.1 单层预算下仍有 19 例 crash,
   中期分析显示其中 18/22 可被 v0.3(G2/G6/G7/G8）离线捕获。
4. **成本**:LLM 时间 +7%,solve +27.7%（可运行代码增多所致，属预期）。

后续臂决策（B''):**值得跑**。guard v0.3 离线检出率 97.0%、误报 0%,
且能覆盖 B' 残余 crash 的 82%(18/22);B''(v0.3 + 闸门，guard 预算可
考虑 2 次/轮以覆盖级联）预期将 crash 残余压到个位数，进一步把失败推向
语义层，为语义约定先验（蒸馏 v0.2）提供更干净的信号。

## B'' 臂全量结果:guard v0.3 在线对照(2026-11-02)

B'' = guard **v0.3** + 闸门,与 B' 同预算(guard 预算 1 次/轮,闸门 ≤2 次/轮,
≤3 轮),唯一变量是规则集 v0.1→v0.3。190 细胞,on 模式。

| 指标 | B'(v0.1) | B''(v0.3) | 变化 |
|---|---|---|---|
| 真成功 | 90 (47.4%) | **103 (54.2%)** | **+6.8pp**(配对净翻转 +13:Bpp-only 21 / Bp-only 8) |
| crash 残余 | 19 | 18 | -1(未达预期) |
| witness_infeasible | 70 | 63 | -7 |
| 逐轮累计(r2/r3) | 30.5%/47.4% | **34.7%/54.2%** | 每轮 +4~7pp |

| LLM 修复调用 | 309 | 301 | 持平 |
| 求解调用 | 235 | 241 | +2.6% |

### crash 残余为何没降到个位数:残余构成分析(18 例逐一归因)

离线预测"v0.3 可捕 B' 残余 22 例中的 18"**在旧总体上成立,但在线总体已
换血**——B'' 的 18 个终态 crash 里:

| 模式 | 例数 | guard v0.3 状态 |
|---|---|---|
| `m.sum(...)`(Model 无 sum 属性) | **8** | **未覆盖——新模式** |
| NotImplementedError(G3 难形态) | 5 | 已预言留给运行时 |
| `m.quicksum`(G4) | 2 | **检出但 LLM 2 次重写未修好**(预算耗尽放行) |
| 语义 KeyError(幻觉键) | 1 | 已预言(需数据契约) |
| `m.getLb` / `Variable.ub` 幻觉 API | 2 | **未覆盖——新模式** |

15/18 的终态 crash 在最后一次 guard 检查中**零命中**——不是 guard 误报或
预算问题,而是规则集不覆盖这些模式。其中 `m.sum` 8 例是本轮新暴露的高频
模式(LLM 把 gurobipy 的 `m.sum()` 习惯带了过来)。

### 结论

1. **v0.3 的价值兑现通道是修复质量而非 crash 计数**:首轮报告完备性
   ×4.4(508 vs 115 次命中),一次重写拿到完整清单,把更多细胞推向
   "出解且语义正确"(+13 净成功),witness_infeasible -7。
2. **自进化闭环验证成立**:B'' 残余自动暴露出 v0.4 的新规则候选
   (`m.sum`、幻觉属性 `getLb`/`ub`),预计可再吸收 ~10/18。挖掘→蒸馏→
   冻结→在线对照的循环可以照原样再转一圈。
3. 同时证实 LLM 修复预算的另一类失效:2 例 G4 检出后重写 2 次仍未修好
   ——对"检出但修不好"的细胞,提高 guard 预算不如把规则写进先验
   (P 臂已证明先验注入几乎消灭 G1–G8 类错误)。
