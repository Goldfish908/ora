# 实验清单 v0.1(截至 2026-11-03 晚)

用途：阶段性整理。每个实验给出设计动机、做法细节、数据位置、结果与结论。
缩写首次出现时给全称。所有数字均可追溯到 `docs/paper/` 下的专项文档与
`runs/` 下的原始记录；本文只做汇总,不引入新数字。

## 0. 共用实验设置

- **任务**:自然语言零售库存优化题 → 大模型生成 PySCIPOpt 建模代码 →
  SCIP 求解 → 导出 solution.json → 校验。
- **模型**:内网 Qwen3.8-27B;主力配置 thinking 开启、temperature 0.6。
- **求解器**:PySCIPOpt / SCIP(开源栈;无 Gurobi)。
- **数据集**:RetailOpt-190——**ReLoop 团队公开基准,非自建**(38 个
  原型 × 5 个数值变体;8 个问题族 F1–F8;ReLoop 论文报告该基准 SOTA
  为 Claude Opus 4.6 的 31.1%)。权属与引用口径见
  `external_baselines_v0.1.md`。
- **主指标·真实成功**:代码可执行 ∧ witness 判语义可行 ∧ 目标值与
  参照解一致(容差 1e-2)。**幻影**:代码可执行、目标值看似一致,但
  witness 重判违例(看似对实则错)。
- **witness**:按族定制的语义规则检查器(Python 脚本,18 条规则),
  对 solution.json 逐条核对(例:订货量落在最小起订量区间即报违例);
  设计动机是代表出题人意图的语义一侧,与求解行为无关。
- **工作流分层**:预求解闸门(生成代码的静态检查)→ 求解 →
  witness 语义校验 → 修复环(≤3 轮,反馈默认 plain 文本)。

## 第一组:问题诊断(motivation 验证)

### E1. 裸模型先导与"誊抄错误"发现(M1:4 个 F1 实例 × thinking 开/关)
- **动机**:测裸模型底力,找大头失败模式。
- **做法**:两种题面模式对比——prompt_full(数据内嵌题面)与
  prompt_schema(数据预加载为变量,物理上不可能誊抄)。
- **结果**:prompt_full 下 4/4 全部死于数据誊抄(把内嵌 JSON 抄成
  Python 语法);切到 prompt_schema 后崩溃率 7/8 → 3/8。
- **结论**:誊抄错误是大头失败模式,测量必须先剥离它——此后全部
  实验固定用 prompt_schema 模式。文档:`motivation_findings_v0.1.md`(F1)。

### E2. witness 重判主表(RetailOpt-190 全量 × on/off,事后重判)
- **动机**:假成功是否普遍?独立语义审计是否必要?
- **结果**:
  | 模式 | 代码可执行 | witness 可行 | 目标值一致 | 幻影 | 真实成功 |
  |---|---|---|---|---|---|
  | thinking 关 | 48/190 | 0 | 0 | 43 | **0(0%)** |
  | thinking 开 | 69/190 | 15 | 15 | 46 | **13(6.8%)** |
- **机制发现**:幻影的违规机制高度一致——全部含"幻影初始库存"
  (规则 C-INIT):模型给第 1 期的非新鲜桶凭空填入库存(免费现货
  替代采购),目标值虚低 7%–45%。根因是题面欠规约(未声明"期初
  库存为零"),**模型系统性地占据规约留下的自由度,而非随机犯错**。
- **结论**:这是 witness 检查器必须独立存在的核心论据。
  文档:`motivation_findings_v0.1.md`(F2)。

### E3. 受控集翻转对(先验覆盖实验)
- **动机**:"连接语义被模型固有先验覆盖"是否真实存在?thinking
  是否加剧?(对应科研线命题:模块间"连接"是难点)
- **做法**:自建受控集,构造翻转对(同一结构两种语义,正确答案
  必须跟随题面翻转);翻转对 v5 达每格 48 样本。
- **结果**:① 先验覆盖真实存在且由先验强度调制——忽略几乎只发生
  在 storage_time(off 35% / on 21%),其余连接 ≤6%;② "thinking
  加剧先验覆盖"**不成立**(on 跟随率全面 ≥ off);③ "on 更容易
  覆盖"扩量后不成立(v4 反向信号是小样本噪声)。
- **结论**:现象(先验覆盖)保住,归因("thinking 有害")拿掉。
  文档:`motivation_findings_v0.1.md`(F5)、`motivation_study_v0.2.md`。

### E4. 合成错误注入审计探针(G1)
- **动机**:检查器的检出下限是多少?
- **做法**:往正确建模里注入人为错误(变量/约束/符号类),看 witness
  与静态检查能否发现。
- **结果**:合成错误 100% 可检出;真实错误显著更难且检出依赖
  thinking。结论:注入探针只证明下限,真实错误更隐蔽。

## 第二组:harness 逐臂建设(工程主线)

### E5. P1:先验注入(memory 第 1 代)
- **动机**:把从历史失败蒸馏的约定(G0–G8 条款)作为先验注入
  prompt,在**生成时刻**预防错误,而非等错误发生后靠反馈环修复。
- **结果**(190 题,on 模式):崩溃率 64%→**7%**;但 pass@1 仅
  6.8%→8.4%(+1.6pp)——崩溃被消灭后错误转化为幻影(出解题中
  90% 幻影)。文档:`priors_pilot_v0.1.md`。

### E6. P2:生成端组合升级(v0.2 先验 + 建模程序脚手架)
- **动机**:E5 证明先验消灭崩溃但成功率几乎不动;同时 ReLoop
  同模型对照显示其 CoT 脚手架单次生成 20.5%,优于我们零样本的
  6.8%——把两者合并进生成端。
- **结果**:pass@1 6.8%→**11.1%**(+63% 相对),成本几乎不变。
  文档:`priors2_pilot_v0.1.md`。

### E7. 预求解闸门(F13 离线 + F14 在线)
- **动机**:在求解之前拦截"注定被 witness 判死"的代码/解,省下
  无效求解预算。
- **做法**:从 263 条历史崩溃台账蒸馏静态检查规则(纯 Python,
  无 LLM 调用);规则版本迭代使离线检出率 73.8%→91.6%→93.9%→
  **97.0%**(255/263),幻影误报 1.9%、成功样本误报 0%;fail-open
  设计(拿不准就放行),闸门对成功样本通过率 84.6%(11/13)。
- **在线对照**(A 臂=仅事后反馈 vs B 臂=+闸门,各 190 题):
  真成功 44.2%→**45.8%**;求解调用 -26.1%,执行墙钟 -16.3%;
  witness 判不可行残余 75→50(-33%),崩溃残余 18→37(+106%)——
  瓶颈从语义层转移到代码健壮性层,符合设计预期。
  文档:`pre_solve_verifier_design_v0.1.md`、`psv_offline_results_v0.1.md`、
  `psv_online_results_v0.1.md`。

### E8. Crash Guard 在线(B' 臂与 B'' 臂)
- **动机**:把崩溃规则做成环内实时拦截器(guard),在修复环里
  即时命中即时改。
- **结果**:B'(guard v0.1 + 闸门)47.4%,崩溃残余 37→19(-49%),
  guard 在 43.5% 的细胞中触发;B''(guard v0.3 + 闸门)**54.2%**
  (103/190,配对净翻转 +13),逐轮累计 r2/r3 = 34.7%/54.2%。
  文档:`crash_guard_mining_v0.1.md`、`crash_guard_online_v0.1.md`。

### E9. P3:语义层 memory 第 2 代(7 条语义惯例 + 族留出协议)
- **动机**:E5–E8 都在管"代码/工具"层;残余错误聚集在语义层
  (witness 判不可行占残余 70%),需要语义级先验。
- **做法**:从反馈轨迹蒸馏 7 条语义惯例(需求恒等、库存平衡、
  初始库存置零、紧 Big-M 等),冻结后注入;族留出协议保证留出族
  不参与蒸馏。
- **结果**:pass@1 11.1%→**21.6%**(近乎翻倍),幻影率 -12.6pp;
  全环(≤3 轮修复)最终 **57.9%**(逐轮:21.6%→55.3%→57.9%);
  F5 族成功率 5%→40%;F3 幻影率反升(70%→85%,留待后续)。
  文档:`semantic_memory_gen2_v0.1.md`。

### E10. 合体臂(P2 生成端 + guard v0.4 + 闸门 + witness 环)
- **动机**:当前技术栈全家桶的单链上限是多少?
- **结果**:pass@1 11.1%,r2 后 39.5%,r3 终态 50.5%——**第三轮
  被 B''(54.2%)反超**。
- **关键发现**:B'' 与合体的成功集合并集 = 132/190(69.5%),
  交集仅 67 题——两条链高度互补,直接催生集成实验(E11/E12)。
  文档:`combo_arm_v0.1.md`。

## 第三组:集成与预算分配

### E11. 双链集成仲裁(A+B):**68.4%**(130/190)
### E12. 三链集成仲裁(A+B+C):**80.5%**(153/190)
- **动机**:E10 发现链间互补性;多条多样化生成链 + witness 仲裁
  是否能零 LLM 成本变现多样性?
- **做法**:纯离线重放,确定性仲裁:收集各链所有轮次中 witness
  判可行的候选,取目标值最小者。三条链:A=无先验生成(54.2%)、
  B=代码惯例 v0.2(50.5%)、C=语义惯例 v0.3(57.9%)。
- **结果**:三链仲裁 80.5%;并集上界(Oracle,需真值)81.6%——
  min-目标值仲裁规则距上界仅 1.1pp。
- **结论**:多样性仍在变现;对部署场景,80.5% vs 单链 57.9% 的
  差值通常远大于 3× 求解成本。文档:`ensemble_dualchain_v0.1.md`、
  `ensemble_trichain_v0.1.md`;图:`docs/paper/figs/ensemble_trichain_v0.1.png`。

### E13. 预算重分配分析(纯离线重放,零新 LLM 调用)
- **动机**:检验"砍掉修复环第 3 轮"的直觉假设。
- **结果**:链 A 第 3 轮边际修复率 29.8%,与第 2 轮 29.9% **持平**
  ——第 3 轮没有崩;原假设不成立。
- **结论**:预算优化方向是"先铺满多样性(链数),再加深轮数",
  以及用自进化提高单链起点。文档:`budget_allocation_v0.1.md`。

### E14. Witness 修复反馈增强消融(A3,负结果)
- **动机**:修复反馈里附带 witness 规则明细(enriched)是否比
   plain 反馈修得好?
- **做法**:59 个残余失败细胞(47 幻影 + 7 目标值一致但解违例 +
  5 次优),双臂对照。
- **结果**:plain 22.0% vs enriched 20.3%,McNemar 检验 9v8——
  干净的负结果。**决策:主线保持 plain 反馈,不并入增强**。
  文档:`feedback_enrichment_v0.1.md`。

## 第四组:外部对照

### E15. ReLoop 同模型移植对照(reloop_ext 仓库,scip-qwen27b 分支)
- **动机**:消除模型差异,同模型、同数据集、同求解器的严格对照。
- **做法**:把 ReLoop 完整管线(无验证 CoT / +L1 修复环两档)移植
  到内网 Qwen3.8-27B + PySCIPOpt。

  ≤3 重生成 + ≤3 修复)**28.4%**(54/190)。**thinking 是准确率的

- **相对位置**:单发口径 我们 P3 21.6% vs ReLoop 20.5%;修复环
  口径(均 ≤3 轮)我们 57.9% vs ReLoop 28.4%;三链集成 80.5%
  (成本 3× 求解)。文档:`reloop_qwen27b_v0.1.md`。

- **做法**:种子 = P3 原样;其余 7 个为删除单一条款/改变块序的

### E18. 第 0 代冠军过拟合闸门

  触发 OVERFIT ALARM。解读:gapcheck60 与全量 190 的 21.6% 一致,

- **生死判据(预先写死)**:(a) 第 3 代冠军 dev40 > 45.0%(同批

  (P3 的 20.0% − 5pp)。(a)∧(c) → 继续;¬(a) → 回退手工+集成
  路线;(a)∧¬(c) → 判过拟合回退。

### E19. 第 1–3 代进化跑批(已收官,LLM 变异无噪声外增益)

  1 个语义块改写、2 个交叉、1 个最长条款删除;dev40 适应度 →
  冠军过 gapcheck60 闸门 → 变异。第 0→1 代变异已实测通过(条款

- **逐代冠军**:gen1 `g1_g0_no_init_draft` dev40 35.0% /

## 第六组:JEV 融入探索

### E20. P0 替身判官校准(LLM-as-judge 路线可行性实测)
- **动机**:JEV(TypeSafe "System One" 决策模型,非 LLM)融入探索的
  第一步——在引入其真身 API 前,先实测"LLM 替身判官"这一最省力
  路线在我们的数据分布上是否及格;同时给 witness 确定性审计的
  必要性提供一个直接对照实验。
- **做法**:Qwen3.8-27B(内网,无思考模式)对 316 个已被 witness
  标注的解题细胞做二分类判定(真成功 / 幻影),并要求输出置信度;
  以 witness 标注为参照系统计混淆矩阵。脚本
  `scripts/judge_calibration_p0.py` + `judge_calibration_p0_analyze.py`。
- **结果**:幻影被误判为通过(false-clear)**45.3%**;真成功被误报
  42.6%;平衡准确率仅 ~53%;判官置信度恒定 0.95,但其"高置信"
  判定实际干净率只有 29%;在 f1 族(幻影库存主场)幻影检出率仅
  14%。
- **结论**:LLM 判官路线在本分布上不及格——与文献中 Opt-Verifier
  的 90% false-clear 同向;witness 的确定性语义审计(误报 1.9%/0%
  实测可控)是目前唯一可信的幻影防线。文档
  `jev_integration_exploration_v0.1.md`。
