# Industry OR 中的可信规范进化：层次化系统与目标感知语义接受机制

状态：研究设计 v0.1。本文区分已获得的实验证据、当前机制设计和仍待验证的研究假设，不将框架完整性等同于实验有效性。

## 摘要

工业优化系统正从“生成一个可执行模型”转向“在动态任务、修复和迁移中持续生成可信决策”。然而，代码可执行、求解器返回最优、目标值优于参考值，都不能保证模型忠实于原始业务语义。单纯依赖弱代理可能接受幻影；单纯要求所有高层检查不变，又会拒绝合理的语义修复。

本文提出一种**可信规范进化**框架：以共享建模规范为生成对象，以局部证据图为修复与审计载体，以版本化验证记忆保存反例、出处和权限，并通过**范围约束、目标感知、证据驱动的语义接受机制**协调生成、验证与迁移。核心研究问题不是如何堆叠 GEPA、DAG 或 memory，而是：

> 当生成规范、局部模型和验证知识都发生变化时，如何既不放过幻影，也不误杀合理的语义修复，并使真实语义增益可以独立评价和跨范围复用？

## 1. Industry OR 背景与研究问题

工业优化任务具有异质业务规则、复杂数据连接和较高的错误部署成本。其挑战不只是自然语言到 MILP 的翻译，还包括：

- 多文件业务数据与字段契约；
- 变量、约束、索引和单位之间的连接；
- 执行、求解、输出和独立业务审计；
- 局部修复引入的新错误；
- 不同题族之间的知识与检查迁移。

由此产生三个研究问题：

1. **共享规范是否比碎片经验和局部修复更能产生真实语义增益？**
2. **验证知识如何初始化、授权和跨族迁移，而不是直接复制旧 Witness？**
3. **如何区分合理语义修复、合理的下游改善与检查洗白？**

本文将“静默错误”或“幻影成功”定义为：系统被弱代理或求解状态认证为成功，但独立业务检查表明输出不满足原始问题。代码崩溃不是唯一风险，表面上更优的错误模型可能更具业务危险性。

## 2. 层次化系统，而非模块堆叠

### 2.1 规范生成层

负责形成和更新共享建模规范：

- 变量、约束和目标组织；
- 业务规则及其连接；
- 求解器 API 与输出契约；
- 可跨题复用的建模知识。

当前实现使用官方 GEPA 作为规范提议器，但 GEPA 本身不是本文的核心算法贡献。规范候选表示为 \(S_v\)，其中 \(v\) 是版本。

### 2.2 局部证据获取层

负责处理单题失败并保存：

- 执行错误与 API 签名；
- 求解状态和目标值；
- 业务违规及坐标；
- 修复前后代码和检查差异；
- 回滚、重复修复与停止原因。

当前实现使用有界 DAG 表示这些修复边，但 DAG 只是证据和路径的组织方式，不是研究目标本身。

### 2.3 独立验证层

负责执行有明确出处和适用范围的检查：

- 执行和输出契约；
- 业务约束与守恒；
- 变量域和激活连接；
- 目标值重算；
- 独立参考解与 clean/wrong 反例；
- UNKNOWN 和未覆盖语义。

治理检查与最终独立评价器必须区分，避免系统仅学会通过自己的考试。

### 2.4 证据记忆与信任治理层

负责保存：

- 规范及父版本；
- 检查函数与代码哈希；
- 题面出处与字段绑定；
- clean/wrong 反例；
- 审计、权限、适用范围和退休历史；
- 规范漂移与未覆盖机制。

memory 在这里首先不是“给生成器增加更多文本”，而是 Witness 和治理层的证据工具。

### 2.5 冻结评价层

负责在配置冻结后独立评价：

- 直接首轮真正确率；
- 修复后真正确率；
- 幻影与 UNKNOWN；
- 新增和丢失真实 win；
- 非目标语义回归；
- memory 迁移收益与误用；
- LLM、token 和求解成本。

测试期间 registry 只读，禁止写回和调参。

## 3. 基本形式化

### 3.1 任务、规范与检查

设：

- 任务为 \(q\)，其业务范围为 \(\sigma(q)\)；
- 当前共享规范为 \(S_v\)；
- 修复前候选为 \(x\)，修复后候选为 \(x'\)；
- 授权检查集合为 \(A(\sigma)\)；
- 检查 \(c\) 的 verdict 为 \(v_c(x)\)。

检查 verdict 包括：

\[
\text{pass},\quad \text{fail},\quad \text{unknown},\quad \text{not\_applicable}
\]

其中：

- `not_applicable` 表示机制未启用，不等于通过了一条语义检查；
- `unknown` 表示检查应当适用但证据不足，不能当作安全；
- `hint_only` 是检查资产状态，不是通过 verdict。

### 3.2 按出处获得局部否决权

候选检查从 `hint_only` 开始。只有同时满足以下条件，才在范围 \(\sigma\) 内获得 `veto_enabled`：

\[
\operatorname{Grounded}(c,\sigma)
\land \operatorname{IndependentAudit}(c,\sigma)
\]

当前原型的最低实现门槛为：

- 至少 3 个 clean 和 3 个 wrong；
- clean 误报为 0；
- precision ≥ 1.0；
- detection ≥ 0.6；
- UNKNOWN = 0。

这些只是实现门槛，不能证明跨族或全局可靠。每条权限都绑定字段、题面出处、代码哈希、父版本和适用范围。

## 4. 核心机制：目标感知的语义接受

### 4.1 为什么两种极端都不可行

**只使用弱代理：** 可能接受目标值更好但业务不可行的解。

**所有高层检查必须不变：** 会把真实的 `fail→pass` 修复与检查洗白一并拒绝。

因此需要一种目标感知、范围受限且证据驱动的接受规则。

### 4.2 目标改善

设本次修复的目标检查为 \(t\in A(\sigma)\)。定义：

\[
\operatorname{TargetOK}(t,x,x')
\iff
(v_t(x)=\text{fail}\land v_t(x')=\text{pass})
\lor
(v_t(x)=\text{pass}\land v_t(x')=\text{pass})
\]

目标不存在、目标仍为 fail、目标变为 fail 或出现 UNKNOWN，均不能作为已完成的目标修复。

### 4.3 非目标回归保护

对任意非目标检查 \(c\neq t\)：

\[
v_c(x)=\text{pass} \Rightarrow v_c(x')=\text{pass}
\]

即不允许非目标 `pass→fail`。UNKNOWN 同样拒绝。

### 4.4 合理的下游改善

定义非目标改善集合：

\[
D=\{c\neq t\mid v_c(x)=\text{fail}\land v_c(x')=\text{pass}\}
\]

当 \(D\neq\varnothing\) 时，只有满足以下条件才允许：

1. 目标检查已改善；
2. 所有适用的授权检查在 \(x'\) 上均为 pass；
3. 没有 UNKNOWN；
4. 规范、修复目标和证据链可追溯。

记最终门禁为：

\[
\operatorname{FinalPass}(x',\sigma)
\]

则接受条件可写为：

\[
\begin{aligned}
\operatorname{Accept}(x\rightarrow x'\mid t,\sigma)
\iff&
\operatorname{TargetOK}(t,x,x')\\
&\land \operatorname{NoUnknown}(x,x')\\
&\land \operatorname{NoNonTargetRegression}(x,x')\\
&\land \big(D\neq\varnothing \Rightarrow \operatorname{FinalPass}(x',\sigma)\big)
\end{aligned}
\]

这里有两个不同决策：

- **修复边接受**：允许经过验证的改善，或保留仍有明确失败但目标已取得局部进展的分支；
- **最终输出接受**：要求所有适用的授权检查通过。

这避免了把“允许目标修复”与“允许任何非目标变化”混为一谈。

## 5. 一个真实的接受案例

在增材微工厂任务中，连续修复过程依次暴露：

1. 错误的 SCIP 间隙参数 `gap/rel`；
2. 错误的 `getSoltime()` API 调用；
3. `getSolTime()` 的参数不匹配。

通过容器内真实 API 签名探测，最终代码正确设置 `limits/gap` 并输出解。官方评价为：

- `feasible = true`；
- `quality = 1.991923112086961`；
- `profit = 11688.043683670841`。

修复前后：

```text
execution_contract:                  fail → pass
manufacturing_official_task_pass:    fail → pass
```

旧规则以“非目标检查发生变化”拒绝这条边，尽管最终官方检查全部通过。新的目标感知规则允许它，因为：

- 目标是执行契约，且已经改善；
- 下游官方任务通过是合理结果；
- 最终所有授权检查均为 pass；
- 没有 UNKNOWN。

这个案例说明：**非目标 fail→pass 不应自动拒绝，但也不能自动接受，必须要求最终验证闭合。**

## 6. 规范与验证记忆的晋升

GEPA 接受只代表代理分提高，DAG 成功只代表单题修复完成，都不能直接形成正式记忆。

规范晋升要求：

\[
\operatorname{IndependentReplay}(S_{v+1},S_v)
\land \operatorname{ChangedFeaturesCovered}(S_{v+1})
\land \operatorname{ScopeConfirmed}(S_{v+1})
\]

具体包括：

- 直接生成相对父规范没有独立语义退化；
- 新增、删除和改变的规则有题面出处；
- 相关 clean/wrong 反例通过；
- 机制和适用范围已确认；
- 未覆盖漂移未被静默隐藏。

状态机为：

```text
candidate
   ↓ 独立重放 + 出处审计 + 范围确认
promoted
   ↓ 测试开始 / 出现可靠反例
frozen / retired
```

原始轨迹、候选资产和已授权资产必须分开保存。

## 7. 跨族与跨数据集迁移

当任务范围从 \(\sigma\) 变为 \(\sigma'\)：

\[
A(\sigma) \not\Rightarrow A(\sigma')
\]

旧检查只能作为 `hint_only` 模板。迁移过程为：

```text
旧检查模板
→ 新字段绑定
→ 新题面出处核验
→ 新 clean/wrong 审计
→ 新范围 veto_enabled
```

可迁移的是：

- 初始化协议；
- 检查模式；
- 反例构造方法；
- 资产生命周期和权限管理。

不能直接迁移的是：

- 具体字段、单位和容差；
- 业务公式；
- 参考解和标签；
- 已获得的否决权。

没有独立业务证据时，只能报告代理指标、覆盖率和 UNKNOWN，不能声称完整业务正确。

## 8. 实验设计

### 8.1 主要对照

| 组别 | 目的 |
|---|---|
| B0：空规范直接生成 | 冷启动基线 |
| B1：GEPA共享规范直接生成 | 共享规范的首轮收益 |
| B2：B1 + 残余局部DAG | 局部修复增量与 win-safe |
| B3：B2 + 经审计的 memory | 后续任务上的迁移收益 |

B3 必须在后续任务上比较，不能用训练过的任务重复评分冒充 memory 泛化。

### 8.2 必要消融

- 原始 R2 / 所有高层 verdict 必须不变；
- 简单 Witness 过滤；
- 目标感知接受；
- 原始文本 memory；
- 带出处和权限的 memory；
- 无跨族重新授权。

### 8.3 指标

分别报告直接生成和 DAG 后结果：

- 真正确率；
- 幻影代理成功；
- UNKNOWN 与不适用；
- 新增和丢失真实 win；
- 合理修复误拒率；
- 非目标语义回归；
- 规范漂移检出率；
- 覆盖与 memory 误用；
- LLM、token 和求解成本。

主曲线必须绑定数据、模型、规范、Witness、参考目标和评价器版本。

## 9. 当前证据与边界

### 9.1 已有支持

**RetailOpt：**

- 静态 seed：20 个代理通过中仅 3 个 Witness 真正确，17 个为幻影，40 个 UNKNOWN；
- 一次短程 GEPA 接受候选：57/60 代理通过、57/60 Witness 真正确、0 幻影、3 UNKNOWN；
- 说明共享规范可以带来真实语义提升，但未证明动态放大或严格 heldout 泛化。

**ORAgentBench：**

- 官方任务评价器能够独立检查业务可行性和目标质量；
- 已跑通制造域 Witness 初始化：3 个 clean 任务和 9 个 wrong 反例，当前审计 precision=1、detection=1、UNKNOWN=0；
- 已完成一条真实 DAG 修复与目标感知接受案例；
- 旧 GEPA 中也观察到 `proxy=true / official true=false` 的 dev 幻影，但迁移重放不完整，memory 未晋升。

### 9.2 尚不能声称

- 动态进化普遍放大错误；
- 完整 R1/R2 或目标感知机制已经在所有数据上有效；
- memory 已经实现跨族复用收益；
- Witness 可以自动通用初始化；
- B0–B3 和严格 heldout 已完成；
- 完整系统达到 SOTA。

当前 ORAgentBench 的两阶段制品生成和关闭 thinking 配置仍属于新协议验证，不能与旧的单阶段结果混成同一曲线。

## 10. 论文贡献的建议表达

建议将贡献组织为：

1. **问题定义**：Industry OR 中代理成功、业务语义与验证权限的错位；
2. **系统框架**：层次化规范生成、局部证据获取、独立验证和证据记忆；
3. **核心机制**：范围约束、目标感知、证据驱动的语义接受和跨范围重新授权；
4. **实验证据**：真实语义增益、幻影减少、合理修复保留、迁移收益与成本边界。

GEPA 和 DAG 在实现与实验设置中说明，不作为算法创新的标题。

论文的核心不是“系统里有很多模块”，而是：

> **一种让生成、修复、验证和迁移都接受统一证据与权限约束的机制，使 Industry OR 系统能够产生可独立确认的语义增益。**
