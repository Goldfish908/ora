# Industry OR 中的可信规范进化：依赖感知、目标约束的修改接受机制

状态：研究设计定稿（final，基于 v0.1 修订）。本文区分已获得的实验证据、当前机制设计和仍待验证的研究假设，不将框架完整性等同于实验有效性。

修订说明（相对 v0.1）：

1. 论文中心从“五层系统”收窄为“修改接受”这一判定问题，五层架构降为实验载体；
2. 检查 verdict 增加 `blocked`，引入检查依赖图，修正“修复前业务检查本应不可评估却被记为 fail”的问题；
3. 修复边区分严格改善、局部进展和无变化，消除 v0.1 中 TargetOK 与“保留局部进展分支”的矛盾；
4. 明确修复目标由控制器在修复前确定，不由修复模型声明；
5. 明确治理检查与最终评价器的关系，并披露当前 ORAgentBench 原型中二者同源的事实；
6. 证据部分更正：RetailOpt 的 57/60 来自 GEPA 选择集，增益中 38 题属于“变得可评估”，16 题属于语义修复；ORAgentBench 的 wrong 反例为输出层人工变异；
7. 主实验改为边级取舍实验，B0–B3 作为系统级补充。

## 摘要

工业优化系统正从“生成一个可执行模型”转向“在动态任务、修复和迁移中持续生成可信决策”。代码可执行、求解器返回最优、目标值优于参考值，都不能保证模型忠实于原始业务语义。

在规范进化和局部修复中，每一步都要回答同一个问题：**是否接受这次修改**。只按代理分接受，可能接受洗白；要求所有高层检查不变，又会拒绝合理的语义修复。这个接受判定本身就是一个有两类错误的决策问题。

本文提出一个**依赖感知、目标约束、按出处授权**的修改接受机制：

- 检查按前置依赖组成图，修复前因前置条件不满足而无法评估的检查记为 `blocked`，与证据不足的 `unknown` 区分；
- 每条修复边的目标检查由控制器在修复前根据失败签名确定；
- 只有经独立审计、有题面出处的检查在其适用范围内拥有否决权；
- 非目标的 `pass→fail` 一律拒绝，非目标的 `fail→pass` 只有在最终授权检查全部闭合时才接受；
- 检查跨范围迁移时只继承模板，否决权必须重新审计。

核心研究问题是：

> 当生成规范、局部模型和验证知识都在变化时，哪一种接受规则能同时少放过洗白、少误杀合理修复，且其判定可以被独立真值检验？

## 1. 背景与研究问题

工业优化任务具有异质业务规则、复杂数据连接和较高的错误部署成本。其挑战不只是自然语言到 MILP 的翻译，还包括多文件数据与字段契约、变量与约束之间的连接、执行与独立业务审计、局部修复引入的新错误，以及题族之间的知识迁移。

本文将“幻影成功”定义为：系统被弱代理或求解状态认证为成功，但独立业务检查表明输出不满足原始问题。代码崩溃不是唯一风险，表面上更优的错误模型可能更具业务危险性。

研究问题：

1. **RQ1（接受判定）**：在修复边和进化边上，代理接受、全检查不变、目标约束接受三类规则的两类错误各是多少？
2. **RQ2（授权）**：检查应如何获得否决权，才能在自然幻影上保持低误报、高检出，而不只是检出人工变异？
3. **RQ3（迁移）**：检查和规范跨题族、跨数据集迁移时，哪些可以继承，哪些必须重新审计？
4. **RQ4（增益分解）**：共享规范和修复带来的增益中，多少来自“变得可评估”，多少来自真实语义修复？

## 2. 系统载体

五层架构是实验载体，不是本文的贡献。GEPA 和 DAG 只在实现与实验设置中说明。

| 层 | 职责 | 当前实现 |
|---|---|---|
| 规范生成 | 提议和更新共享建模规范 \(S_v\) | 官方 GEPA |
| 局部证据获取 | 记录单题失败、修复前后代码与检查差异、停止原因 | 有界修复 DAG |
| 独立验证 | 执行有出处、有范围的检查，返回 verdict | Witness 与执行契约 |
| 证据记忆与信任治理 | 保存检查、出处、反例、权限、适用范围和退休历史 | 版本化 registry |
| 冻结评价 | 配置冻结后独立评价，测试期只读 | 官方任务评价器 / Witness 重放 |

**治理检查与最终评价器的关系必须显式声明。** 治理检查用于接受判定，最终评价器用于报告结果。若二者使用同一个判定函数，系统在 dev 侧就是在针对最终指标做选择，此时只能报告“对最终评价器的拟合程度”，不能报告“治理带来的独立增益”。当前 ORAgentBench 原型中，`<domain>_official_task_pass` 检查直接调用官方任务评价器（见 9.1），这一点在论文中必须披露，正式实验需要改为由 dev/audit 侧初始化、与官方评价器实现无关的检查。

工程上，以上分工对应 `industry-decision-model` 仓库：一次修复回合即一条边 \(x\rightarrow x'\)，`transition.json` 记录前后评分；可信评测器对应冻结评价层。要支持本文机制，需要在 ScoreReport 中加入逐检查 verdict 向量，并将治理检查插件与最终评测器分开登记指纹。

## 3. 形式化

### 3.1 任务、检查与 verdict

设任务为 \(q\)，业务范围为 \(\sigma(q)\)，当前共享规范为 \(S_v\)，修复前候选为 \(x\)，修复后候选为 \(x'\)。授权检查集合为 \(A(\sigma)\)，其余检查为 `hint_only`。

检查 \(c\) 的 verdict \(v_c(x)\) 取值：

| verdict | 含义 |
|---|---|
| `pass` | 前置条件满足，检查通过 |
| `fail` | 前置条件满足，检查不通过 |
| `blocked` | 前置检查未通过，本检查无法评估 |
| `unknown` | 本应可评估，但证据不足或检查出错 |
| `not_applicable` | 该机制在本任务中未启用 |

`not_applicable` 不等于通过；`unknown` 不能当作安全；`blocked` 也不是 `fail`，它表示没有信息。

### 3.2 检查依赖图

检查之间存在前置依赖，组成有向无环图 \(G\)。典型层次为：

```text
执行成功 → 导出完整 → 变量域 / 字段绑定 → 业务约束 → 目标值重算 / 最优性
```

若 \(c\) 的任一前置检查不为 `pass`，则 \(v_c(x)=\text{blocked}\)。

这一区分是必要的：程序崩溃时，业务检查本来就无法运行。若把这种状态记为 `fail`，“修复执行”会被计作“修复业务”；若记为 `unknown`，任何从崩溃修到可运行的修复都会因 NoUnknown 被拒绝。

### 3.3 按出处获得局部否决权

检查从 `hint_only` 开始。在范围 \(\sigma\) 内获得 `veto_enabled` 需要：

\[
\operatorname{Grounded}(c,\sigma)\land\operatorname{IndependentAudit}(c,\sigma)
\]

- Grounded：检查绑定字段、题面出处、代码哈希、父版本和适用范围；
- IndependentAudit：在 clean 与 wrong 样本上审计。

当前原型门槛为：至少 3 个 clean 与 3 个 wrong、clean 误报 0、precision ≥ 1.0、detection ≥ 0.6、`unknown` = 0。

这个门槛在统计上很弱：3 个 clean 上零误报，只能给出真实误报率约 63% 的 95% 置信上界（零失败时上界约为 \(1-0.05^{1/n}\)）。正式实验需要：

1. 报告每条授权检查的 clean/wrong 样本数和误报率置信区间；
2. wrong 样本优先使用**自然产生的错误**（例如 RetailOpt 的自然幻影），人工变异只作补充；
3. 分别报告对执行层变异和对语义错误的检出率。

## 4. 核心机制：依赖感知、目标约束的修改接受

### 4.1 两种极端为什么不可行

- **代理接受（R0）**：只要代理分提高就接受，可能接受目标值更好但业务不可行的修改；
- **全检查不变（R1）**：要求目标层以上所有授权检查 verdict 不变，会把真实的 `fail→pass` 修复与洗白一并拒绝。

### 4.2 修复目标由控制器确定

每条修复边在生成修复之前，由控制器根据失败签名确定目标检查 \(t\)，并写入证据链。修复模型不能声明或更改目标。否则模型可以任选一个失败检查作为目标，规则失去约束力。

当前实现满足这一点：执行契约失败时目标为 `execution_contract`，否则为该领域的任务检查。

### 4.3 修复边的三种情况

对目标检查 \(t\)：

| 情况 | 条件 | 处理 |
|---|---|---|
| 严格改善 | \(v_t(x)\in\{\text{fail},\text{blocked}\}\)，\(v_t(x')=\text{pass}\) | 可接受 |
| 局部进展 | \(v_t(x)=v_t(x')=\text{fail}\)，且 \(t\) 的违例幅度严格下降、无新增违例项 | 可保留为分支，不作为最终输出 |
| 无变化或退化 | 其余情况，包括 `pass→pass` | 拒绝 |

v0.1 将 `pass→pass` 计入目标通过，会使目标本已通过的无效修改被接受，本版删除。局部进展沿用修复控制器中的“违例幅度下降且违例集合不变”定义。

### 4.4 非目标回归保护

对任意非目标授权检查 \(c\ne t\)：

\[
v_c(x)=\text{pass}\Rightarrow v_c(x')=\text{pass}
\]

即非目标 `pass→fail` 一律拒绝。修复后出现 `unknown` 同样拒绝。

修复前为 `blocked` 的非目标检查，修复后变为可评估时，按其新 verdict 处理：变为 `pass` 计入下游改善，变为 `fail` 则表示修复暴露了新的问题，边不拒绝，但不能作为最终输出。

### 4.5 下游改善与最终闭合

定义非目标改善集合：

\[
D=\{c\ne t\mid v_c(x)\in\{\text{fail},\text{blocked}\}\land v_c(x')=\text{pass}\}
\]

\(D\ne\varnothing\) 时，只有当所有适用的授权检查在 \(x'\) 上都为 `pass`（记作 \(\operatorname{FinalPass}(x',\sigma)\)）时，才允许把 \(x'\) 作为最终输出。

接受条件为：

\[
\begin{aligned}
\operatorname{Accept}(x\rightarrow x'\mid t,\sigma)\iff
&\ \operatorname{TargetProgress}(t,x,x')\\
&\land\ \operatorname{NoUnknown}(x')\\
&\land\ \operatorname{NoNonTargetRegression}(x,x')\\
&\land\ \big(D\ne\varnothing\Rightarrow\operatorname{FinalPass}(x',\sigma)\big)
\end{aligned}
\]

其中 TargetProgress 为 4.3 中的严格改善或局部进展。两个决策必须分开：

- **修复边接受**：允许严格改善和局部进展进入 DAG；
- **最终输出接受**：要求所有适用授权检查为 `pass`。

### 4.6 未授权检查上的回归

回归保护只覆盖授权检查，而洗白最可能发生在没有否决权的地方。因此：

- `hint_only` 检查上的 `pass→fail` 不否决，但必须逐边记录并单独报告；
- 该比例作为“规则覆盖之外的洗白风险”指标，与授权检查上的拒绝率一起报告。

### 4.7 机制的可检验性质

在授权检查无误报的前提下，按本规则接受的修复链满足单调性：任一授权检查一旦在前置条件满足时为 `pass`，在后续被接受的边上不会变为 `fail`。这一性质本身简单，但它把“可接受的修改”定义成可被独立真值检验的对象，并使两类错误可以在边级别测量。

## 5. 一个真实的接受案例

在 ORAgentBench 增材微工厂任务中，连续修复依次暴露：

1. 错误的 SCIP 间隙参数 `gap/rel`；
2. 错误的 `getSoltime()` API 调用；
3. `getSolTime()` 的参数不匹配。

通过容器内真实 API 签名探测，最终代码正确设置 `limits/gap` 并输出解。官方评价为 `feasible = true`、`quality = 1.991923112086961`、`profit = 11688.043683670841`。

修复前后：

```text
execution_contract:                  fail → pass
manufacturing_official_task_pass:    fail → pass
```

R1 以“非目标检查发生变化”拒绝这条边。本规则允许它：目标是执行契约且严格改善；下游任务检查的变化属于 \(D\)；最终所有授权检查为 `pass`；没有 `unknown`。

需要如实说明三点：

1. 按 3.2 的定义，修复前任务检查应为 `blocked` 而非 `fail`，当前原型把“无解可评”记为 `fail`；
2. 案例中的任务检查直接调用官方评价器，治理判定与最终评价同源；
3. 这是单个案例（n=1），只说明 R1 存在误杀，不能估计误杀率。

## 6. 规范与验证记忆的晋升

GEPA 接受只代表代理分提高，DAG 成功只代表单题修复完成，二者都不能直接形成正式记忆。

规范晋升要求：

\[
\operatorname{IndependentReplay}(S_{v+1},S_v)\land\operatorname{ChangedFeaturesCovered}(S_{v+1})\land\operatorname{ScopeConfirmed}(S_{v+1})
\]

具体包括：直接生成相对父规范没有独立语义退化；新增、删除和改变的规则有题面出处；相关 clean/wrong 反例通过；适用范围已确认；未覆盖漂移没有被静默隐藏。

```text
candidate
   ↓ 独立重放 + 出处审计 + 范围确认
promoted
   ↓ 测试开始 / 出现可靠反例
frozen / retired
```

原始轨迹、候选资产和已授权资产分开保存。晋升所用的独立重放集合不得与 GEPA 的选择集重合。

## 7. 跨族与跨数据集迁移

当任务范围从 \(\sigma\) 变为 \(\sigma'\)：

\[
A(\sigma)\not\Rightarrow A(\sigma')
\]

旧检查只能作为 `hint_only` 模板，迁移过程为：

```text
旧检查模板 → 新字段绑定 → 新题面出处核验 → 新 clean/wrong 审计 → 新范围 veto_enabled
```

可迁移的是初始化协议、检查模式、反例构造方法、资产生命周期和权限管理。不能直接迁移的是具体字段、单位和容差、业务公式、参考解和标签，以及已获得的否决权。

已有证据支持这一限制：族内 Witness 在 MAMO / NLP4LP 上 100% 为 `unknown_schema`。没有独立业务证据时，只能报告代理指标、覆盖率和 `unknown`，不能声称业务正确。

## 8. 实验设计

### 8.1 主实验：边级取舍

这是回答 RQ1 的核心实验，大部分可以用已有产物离线完成。

1. **收集边**：RetailOpt 的 GEPA 父子边（逐题展开）、ORAgentBench 的 DAG 修复边、IndustryOR 8 道注册题的 DAG 边；
2. **独立标注**：用最终评价器或 Witness 将每条边标为 改善 / 无变化 / 洗白（代理改善但真值变差或幻影） / 回归；
3. **应用规则**：对同一批边分别应用
   - R0：代理接受；
   - R1：目标层以上授权检查全部不变；
   - R2：本文规则；
   - R2−dep：去掉依赖图与 `blocked`；
   - R2−final：去掉最终闭合条件；
4. **报告**：每种规则接受的洗白边数、拒绝的改善边数、`hint_only` 回归数，以及各自的置信区间。

判读方式：如果 R0 在这批边上几乎不出错，说明现有场景不足以区分规则，需要构造更难的场景（GEPA 更多代、更弱代理、IndustryOR 非注册题），而不是直接宣称机制有效。

### 8.2 系统级对照

| 组别 | 目的 |
|---|---|
| B0：空规范直接生成 | 冷启动基线 |
| B1：GEPA 共享规范直接生成 | 共享规范的首轮收益 |
| B2：B1 + 残余局部 DAG | 局部修复增量与 win-safe |
| B3：B2 + 经审计的 memory | 后续任务上的迁移收益 |

B3 必须在后续任务上比较，不能用训练过的任务重复评分冒充泛化。所有组别的规范选择不得使用最终评价任务。

### 8.3 必要消融

- 接受规则：R0 / R1 / R2 / R2−dep / R2−final；
- 检查授权：人工变异审计 / 自然错误审计；
- memory：原始文本 / 带出处和权限；
- 迁移：继承否决权 / 重新授权。

### 8.4 指标

分别报告直接生成和修复后结果：

- 真正确率，并拆分为“变得可评估”与“语义修复”两部分；
- 幻影代理成功；
- `unknown`、`blocked` 与 `not_applicable`；
- 新增和丢失的真实 win；
- 合理修复误拒数、洗白接受数；
- 非目标语义回归（授权检查与 `hint_only` 分开）；
- 规范漂移检出率；
- 覆盖与 memory 误用；
- LLM、token 和求解成本。

主曲线必须绑定数据、模型、规范、Witness、参考目标和评价器版本，并标明每个数字是否来自选择集。

## 9. 当前证据与边界

### 9.1 已有支持

**RetailOpt（gapcheck60，F1–F4）**

- 静态 seed：代理通过 20/60，其中 Witness 真正确 3、幻影 17；`unknown` 40/60。幻影占代理成功的 85%（该候选上的条件比例）；
- 一次短程 GEPA 接受候选：57/60 代理通过、57/60 Witness 真正确、0 幻影、3 `unknown`；
- 父子边逐题分解：幻影→真正确 16，`unknown`/其他→真正确 38，真正确→真正确 3；新增幻影 0，正确变错 0；
- 典型幻影案例：`retail_f3_storage_bottleneck_v2` 目标值低于参考 36.9%，SCIP optimal，但违反 `C-INIT` 与 `C-DEMAND`。

**ORAgentBench**

- 官方任务评价器可独立检查业务可行性和目标质量；
- 制造域检查初始化：3 个 clean 任务、9 个 wrong 样本，审计 precision=1、detection=1、`unknown`=0；
- 一条真实 DAG 修复与目标约束接受案例（第 5 节）；
- 旧 GEPA 中观察到 `proxy=true / official=false` 的 dev 幻影，但迁移重放不完整，memory 未晋升。

**跨数据集**：族内 Witness 在 MAMO / NLP4LP 上 100% `unknown_schema`。

### 9.2 对已有证据的限定

1. **RetailOpt 的 57/60 来自 GEPA 选择集。** gapcheck60 是 GEPA 的 valset，用于逐代验证和候选选择，且与训练集 dev40 同属 F1–F4。它只能作为选择集表现报告。
2. **这条边上，代理接受没有放大错误，反而修复了 16 个幻影。** 因此本文不以“自进化放大错误”为动机；动机是“代理与真值静态分离，而接受规则决定进化是修复还是洗白”。
3. **增益主要来自“变得可评估”。** 54 题增益中 38 题从 `unknown`/其他变为真正确，16 题为语义修复。两类必须分开报告。
4. **ORAgentBench 的 wrong 样本是输出层人工变异**（缺失解文件、表头错误、空解，3 种 × 3 任务）。detection=1 只说明能检出这三类输出错误，不说明能检出语义错误。
5. **ORAgentBench 的任务检查与官方评价器同源。** 正式实验前需要替换为独立初始化的检查。
6. **机制证据为单案例。** R1 存在误杀已被观察到，误杀率、洗白接受率均未测量。

### 9.3 尚不能声称

- 动态进化普遍放大错误；
- 本文接受规则在任何数据上优于 R0 或 R1；
- 授权检查能检出自然语义错误；
- memory 已实现跨族复用收益；
- Witness 可以自动通用初始化；
- B0–B3 和严格 held-out 已完成；
- 完整系统达到 SOTA。

当前 ORAgentBench 的两阶段制品生成和关闭 thinking 配置仍属于新协议验证，不能与旧的单阶段结果混成同一曲线。

## 10. 定位与贡献

### 10.1 与相关工作的区别

近期工作从不同角度处理代理信号问题：用固定或保密的核心集监测自进化中的能力漂移（HackProbe, arXiv 2609.04665）、以确定性验收检查约束 LLM 评审（PROCTOR, arXiv 2609.02246）、在权重、选择与提示三种途径上统一分析奖励投机（arXiv 2609.25848）、研究记忆式自改进中的错误复现（arXiv 2610.27406）。以上判断基于摘要，正式写作前需精读全文确认。

它们主要回答“分数是否可信”。本文回答“每一个修改是否可以接受，由哪些检查、在什么范围内、依据什么出处来决定”，并把接受判定作为可以在边级别独立检验的对象。

### 10.2 贡献

1. **问题定义**：将修复与进化中的“修改接受”形式化为有两类错误的判定问题，并给出幻影、洗白、误杀的边级定义；
2. **机制**：依赖感知（`blocked` 与检查依赖图）、目标由控制器确定、按出处授权、非目标回归保护与最终闭合分离的接受规则，以及跨范围重新授权；
3. **测量协议**：边级取舍实验与增益分解（可评估性增益 vs 语义增益），在 RetailOpt、ORAgentBench、IndustryOR 上用独立真值检验规则；
4. **实验证据**：两类错误的权衡、`hint_only` 回归、迁移时的授权失效与重建成本。

GEPA、DAG 和五层系统在实现与实验设置中说明，不作为算法创新的标题。
