## 0. 一页摘要

**要解决的问题。** LLM 把自然语言优化问题写成 MILP 时，会出现"静默错误"：模型能跑、能给出最优值，但漏掉或写错了一条需求。不使用标签的验证方法有很多种：多采样一致、参考值比对、证伪测试、语义锚点、单一来源 IR。它们共同的弱点是：**当多个生成结果一起犯同一个错误时，它们都看不出来**（共同原因错误）。

**我们的做法。** 每道题建立两个相互独立的建模通道：代码通道直接写求解代码；IR 通道先抽取逐条需求，再编译成模型。两者交叉核对。"否决权"不默认给任何检查，必须在开发数据上通过统计审计（有限样本下的误拒率上界）才能获得。只有获得授权的检查全部通过，答案才交付，否则标为"未核实"。修复受两条约束：一是按"松弛方向"决定修哪一方，二是修复时不能看到另一通道的结果，以免两边互相迁就、洗白分歧。

**目前的证据（v0.1，Qwen3_8-27B，seed 0）。**
- ORBench v3 mamo_complex（181 题）：全覆盖准确率 148/181，首轮 127/181（配对 21:0，p = 1e-6）；交付题正确率 131/136 = 96.3%。在同一批答案上，"两通道一致"作为交付门，比"同模型 3 份样本一致"交付得更多（136 对 124），错得更少（5 对 6）。
- ORBench v3 IndustryOR（87 题，开发时用过）：全覆盖 77/87，首轮 72/87；交付题正确率 74/78。
- 交付出去的 9 个错误答案，CodeT 式和只用 IR 也全部答错。这类错误目前没有任何方法能发现。
- 需求驱动的修复在 v0.1 中没有改对任何一题；注入修复在开发集上有害，已关闭。

**最大的缺口。** 只有 1 个模型、1 个种子、2 个测试集，公开版本只覆盖了一部分；ReLoop 和 OPT-Kraken 这两个基线还没跑；参考答案的质量还没核实（W1 正在做）；机制 B（修复边接受）还没有正面证据。

## 1. 研究问题和中心主张

### 1.1 研究问题

- **RQ1（现象）**：LLM 生成的优化模型里，共同原因错误有多大比例？漏掉的需求在"题面明写 / 需要推导 / 依赖惯例"三类中怎样分布？
- **RQ2（交付）**：在不使用标签的部署环境下，能否给出一个交付规则，使交付答案的错误率可控，并且覆盖率高于同等成本的基线？
- **RQ3（修复）**：在什么条件下可以安全地修改模型？怎样避免修复把分歧"洗白"成虚假一致？
- **RQ4（授权成本）**：一类检查要获得否决权，需要多少、什么样的独立证据？什么时候必须弃权？
- **RQ5（进化）**：用 GEPA 一类方法进化抽取器或检查时，能否保住统计保证，并且泛化到没见过的问题族？

### 1.2 中心主张（可证伪的形式）

> **主张 A（现象）**：在多个基准和多个模型上，同模型多采样一致、单一来源 IR 一类不依赖标签的检查，漏掉的错误中有相当比例是共同原因错误；这些错误集中在需要推导的需求和依赖惯例的需求上（具体比例由实验给出）。
>
> **主张 B（方法）**：以"相互独立的建模通道一致"为交付依据、以统计审计授予否决权，在相同的交付错误率目标下，覆盖率高于同模型自一致和 LLM 评审一类的交付规则；在不同数据集之间，误拒率保持在审计给出的界以内。
>
> **主张 C（修复）**：按松弛方向决定修复哪一方、修复时隔离另一通道的信息，比朴素修复（任意注入，或让一方看到另一方的结果）改坏的更少、洗白的更少。

**证伪条件**（写在这里，避免事后挑选）：
- 主张 A：共同原因错误所占比例很小（例如低于 10%），或者三类需求的遗漏分布没有差异。
- 主张 B：在至少两个测试集、两个模型上，两通道交付门都不能在风险-覆盖上优于自一致门。
- 主张 C：在真实重跑中，按方向修复的"改对 / 改坏"比不优于朴素注入，或者隔离修复和交叉修复的交付错误率没有差别。

### 1.3 主张的收窄历史（审稿人可能会追问）

- 最初的主张是"静默错误主要来自题面没写明的惯例"。用户审阅指出（2026-11-24）：F1–F4 主总体的 70 个样本里，违规只涉及 C-INIT（58 个）和 C-DEMAND（28 个）；当时的分类把这两条分别算作隐含和明文。因此证据只支持"LLM 系统性地漏掉明文和可推导的需求；当需求、生成模型和检查器共享同一个不完整的表示时，内部检查会一起失效"，**还不能支持"主要来自惯例"**。
- 按场景重新标注后（M15），C-INIT 在 95 个场景里属于惯例，C-DEMAND 在不同场景里分别是明文（10）、隐含（35）、待人工核对（55）。全局标签和按场景标签会给出完全相反的结论：用全局标签，隐含需求召回是 155/160，按场景标注只有 16/46。
- 所以论文采用两层写法：**实证层**测三类需求各漏多少、各通道能检出多少；**理论层**的不可区分性结论（P10）只适用于"既没写明、也推导不出"的需求，不外推到所有需求。

**可以独立成立的创新点**（相关工作调研的判断是：没有一项主张作为整体是全新的，见 `spec_first_related_work_v0.1.md`）：
1. 按"场景 × 需求 × 出处"度量遗漏和通道盲区（方法学贡献，有 M15 的反转作为直接证据）。
2. 按作用范围授予否决权，区分出处、绑定、独立证据和统计授权四个层次。
3. 修复边的决策层接受规则（按松弛方向、目标值反证据、隔离通道信息），目前**还没有正面证据**。
4. 授权成本分析：在不同标签条件下，系统能拿到多少否决权、需要多少标注。

**不宜单独作为核心创新的**（用户审阅意见，2026-11-24）：P1–P10 的数学本身；给定正确规格后的子 MILP 修复；直接重优化、Pareto、Merge 等搜索机制；双向差分测试、证伪测试、IR 编译通道本身；单纯的逐检查 RL 奖励设计。

## 3. 问题设定（形式化草稿）

**符号。**
- 题目 x，题面文本 T(x)，可选数据 D(x)，作用范围 σ(x)（数据集或问题族）。
- 通道 k ∈ {code, ir}，生成模型 M_k(x)，求解得到最优值 f_k、解 z_k、状态 s_k、间隙 g_k。
- 检查集合 𝒞 = 𝒞_sys ∪ 𝒞_req，前者是系统一致性检查，后者是 IR 抽取出的逐条需求检查。
- 每条检查 c 在决策 z 上给出判定 v_c(z) ∈ {pass, fail, unknown, blocked, not_applicable}。
- 授权集合 𝒜(σ) ⊆ 𝒞，每个作用范围单独审计、冻结。
- 交付规则：当且仅当 z 上所有适用的 c ∈ 𝒜(σ) 都判 pass 时交付，否则输出"未核实"，同时给出 best_available。
- 指标：覆盖率 = P(交付)，交付风险 = P(答案错 | 交付)。

**独立性假设（必须写清楚，也最容易被质疑）。**
- 理想假设：给定题目 x，两个通道的错误事件条件独立。
- 实际情况并不满足：两个通道是同一个 LLM 生成的；非 RetailOpt 题目中，代码通道的命名表来自 IR，两边共用变量结构（框架审阅 §1.5）；两边读的是同一段题面，对同一句歧义文字可能做出同样的误读。
- 所以论文不能主张"条件独立"。应定义**共同原因残差** ρ(σ) = P(两通道都错且一致 | σ)，用实验测出它，并说明它是交付风险的下界来源。

**授权（统计审计）。**
- 对一条检查 c 和作用范围 σ，在开发数据上收集干净样本（已知正确的决策）和错误样本。
- 授权条件：干净样本至少 59 个、误拒 0 次（单侧 95% 误拒率上界 ≤ 5%）；错误样本至少 3 个、检出率 ≥ 0.6；unknown 为 0。
- 固定的合取检查在共享样本池上统一授权，不需要对每条检查再做 Bonferroni 校正，但检查集合、作用范围和合取方式必须**事先固定**。
- **问题**：样本独立性。同一场景的多个决策不独立；GEPA 选出的候选不是独立同分布抽样；最优点、被筛选过的候选和部署时靠近约束边界的自然解，分布并不相同。所以主要判定应按场景簇计，逐条二项区间只作辅助。

**交付风险的分解（待写成命题）。**
若交付规则只依赖"两通道目标值一致"，则

  P(错 ∧ 交付) ≤ P(两通道都错且目标值一致) + P(只有一方错，且一致检查没检出)。

第二项由审计的检出率控制，第一项就是 ρ(σ)，审计控制不了，只能测量。这个分解能把"为什么共同原因残差是核心问题"和实验直接连起来。**这个命题还没写成正式形式。**

## 5. 方法（系统）

### 5.1 v0.1（已冻结，dc97212）

流程：抽取 IR（必要时修一次）→ 建需求注册表 → 生成代码（零成本 API 修补 → 必要时修一次执行错误）→ IR 编译求解 → 交叉检查 → 证书 → 未交付时进入修复控制（裁决、注入、删除）→ 对照组。每题最多 4 次 LLM 调用。逐组件的输入、输出和效果见框架审阅文档。

### 5.2 v0.2（正在做）

- 循环修复，每个通道最多 3 轮；修复时只用本通道自己的证据，另一通道的目标值和解不进 prompt；修复后才达成的一致单独审计。
- 修复触发条件扩展到"能执行但不可行"（mamo 有 30 题代码、18 题 IR 属于这种情况，v0.1 都没有修复）和"两通道不一致"。
- 机制 B：按松弛方向决定修哪一方；目标值大幅变差且两通道仍不一致时作为反证据；考虑修复后两通道是否一致。
- 盲裁决候选：裁决 prompt 只给需求、引用和题面，不给通道证据（v0.1 的裁决 prompt 会先告诉 LLM"代码违反了这条需求"，有诱导嫌疑）。
- 不交付时按检查结果选通道，不再固定代码优先。
- 差分测试和证伪测试：改成只在两通道一致后运行，专门找共同原因错误；或者移出默认流程。
- IR 通道稳定性：API 命名、白名单、时限、修复预算。
- 探索不依赖 IR 的变量命名方式，解决独立性耦合。
- 重做同模型对照组（CodeT 式和多数投票完全相同），所有对照组都套用同样的零成本 API 修补。
- 事先定好交付错误率目标。

### 5.3 外环进化（计划，v0.2 冻结后）

- **进化对象**：抽取 prompt、IR 写法说明、修 IR 的 prompt。第二轮再考虑 RetailOpt 惯例库。代码通道的 prompt 固定，避免两个通道用同一个 fitness 一起进化，独立性变差。不进化函数。
- **fitness**：IR 可执行率、IR 编译后的目标值是否等于参考值、两通道一致率、抽取精度（惩罚多抽出来的需求，因为它会带来误否决的风险）。**不使用 witness**，避免把金标准规则写进 prompt。
- **数据划分**：进化集、选择集、审计、测试分开；RetailOpt 内部按问题族留出（三族进化、一族选择、轮换）；LogiOR、ComplexOR 纳入 fitness，防止只对 RetailOpt 有效。
- **每轮都要重新审计**：授权绑定 cell 级程序哈希，prompt 一改授权就失效。
- **谱系**：每个候选是 EvidenceDAG 中的一个节点。
- **预算估计**：1000–1500 万 token，按族留出时再加 30–50%。

### 5.4 非参数 harness 进化（更后面）

把路由、修复路线、交付规则本身当作进化对象，用固定回归集把关，且不能改坏任何首轮正确的题。风险最高，放在最后。

### 5.5 witness 的位置

最终框架和论文方法都**不依赖 witness**。witness（RetailOpt 的手写规则检查器）只在评测层使用：RetailOpt 开发集评分，以及授权审计中"错误样本"的标签。使用前要做 witness 审计（零 LLM 审计工作流 Part 4 已完成初版），标出从未在 F1–F4 上触发的规则、被 F5–F8 校准污染的规则，并冻结版本。面对一个全新的数据集时，框架照常运行；能评测到什么程度，取决于该数据集有什么标签（见 §6.6 的三档）。

### 6.4 指标

- 全覆盖准确率、仅交付准确率、首轮准确率。
- 覆盖率、交付风险、风险-覆盖曲线和 AURC、给定风险目标下的覆盖率。
- 交付错误按方向拆分（比参考值好 / 差）；认证幻影数（交付答案严格优于参考值）。
- 授权审计：每条检查的干净样本数、错误样本数、误拒率上界、检出率、独立簇数。
- 外部误拒率：测试集上两通道都对、但一致检查判失败的比例。
- 成本：每题 LLM 调用数、token 数、求解次数。
- 统计：McNemar 精确检验（配对）、按簇自助法区间（RetailOpt 按原型，其他按题），多重比较要事先说明。

### 6.5 消融（计划）

| 消融 | 回答什么 | 类型 |
|---|---|---|
| 去掉 IR 通道，改用自一致门 | 独立通道是否必要 | 已有事后计算；需真实重跑 |
| 共享命名表 vs 独立命名 | 命名耦合带来多少共同原因 | v0.2 |
| 隔离修复 vs 交叉修复（修复时能看到另一通道） | 是否会洗白 | v0.2，**关键实验** |
| 循环轮数 1 / 2 / 3 | 循环的边际收益 | v0.2 |
| 机制 B：任意注入 / 按类型 / 按方向 / 按方向加目标值反证据 | 主张 C | v0.2 |
| 盲裁决 vs 带证据的裁决 | 裁决是否被诱导 | v0.2 |
| 有授权 vs 无授权（所有检查都只作提示，或都有否决权） | 授权的作用 | 可从现有记录事后计算，再做重跑 |

### 6.6 泛化设计

- **跨数据集**：ORBench 上已有：外部误拒 0，交付题正确率 95–96%。
- **跨族**：F1–F4 上全部开发完成并冻结后，F5–F8 只跑一次。主口径对照重解的参考值（带对偶界）；witness 判定作辅口径，被污染和未验证的规则单列或排除。
- **标签条件的三档**：无标签（只能测交付率）、有参考答案（可测准确率和外部误拒率）、有逐条需求标签（可在该领域授权更多检查）。这三档本身就是"授权成本分析"的框架。

### 6.7 预算

- v0.1 共用 1021 万 token；v0.2 上限 2500 万。
- 补齐主实验（更多数据集、模型、种子、ReLoop 和 OPT-Kraken 基线）：粗估 4000–6000 万，取决于新模型的调用成本。
- 外环进化：1000–1500 万，按族留出另加 30–50%。
- **这些估计都很粗**，超出用户此前同意的 8000 万总上限的可能性不小，需要逐项确认。

## 9. 不确定、可能被质疑的地方（完整清单）

### 9.1 主张和动机

1. **"共同原因错误"的规模可能被标签错误放大。** 交付错误中有一部分可能是参考答案错了（IndustryOR 3 个"比参考值好"，LogiOR 4 个，MAMO 211 与 v3 标签 13:0 的单向差异）。W1 正在核实。如果大部分是标签错误，主张 A 会明显变弱。
2. **"主要是惯例"已经不成立**，现在的说法是"三类需求分层度量"。审稿人可能会问：既然大部分遗漏是明文和可推导的需求，为什么不直接用更强的模型或更好的 prompt？需要给出"更强模型也一起错"的证据，这依赖多模型实验。
3. **按场景标注需求类型有主观性。** 有 55 个 C-DEMAND 场景标为待人工核对；C-INIT 到底是惯例还是可推导，也需要人工确认（零 LLM 审计 P4 的开放点）。标注规则必须公开，最好有第二人标注并报告一致性。
4. **RetailOpt 是作者自己构造的数据。** 审稿人会质疑代表性。核心结论必须在公开数据集上成立，RetailOpt 只用于逐条需求的分析。

### 9.2 方法

5. **独立性不成立。** 同一个 LLM、同一段题面、共享命名表。必须量化共同原因残差，并在论文里避免"独立通道"这种绝对说法，改为"来源分离的通道"。
6. **IR 通道本身不新**（IR2Solve），**证伪测试不新**（2607.16646），**差分测试是老方法**（McKeeman 1998）。必须明确这些是复用，贡献在组合方式和授权。
7. **授权的统计保证依赖样本独立性和同分布。** 开发集只有 20 个 RetailOpt 原型簇；LogiOR 和 ComplexOR 是不同来源；测试分布不同。跨数据集时 P6 的保证在形式上不成立，只能用实测的外部误拒率作为经验证据。
8. **只有一条检查拿到授权**，"按作用范围授权"这套机制在实际中几乎退化成"两通道一致才交付"。审稿人可能会说机制很复杂、实际只用了最简单的规则。应对：把它写成授权成本分析的结论（大多数检查拿不到授权，说明需要更多独立证据），并展示在有逐条标签的领域（RetailOpt）能拿到更多授权的条件。
9. **机制 B 没有正面证据。** 如果 v0.2 的按方向修复在真实重跑中也不能稳定地改对，贡献 3 只能降级为诊断性结论："单凭 LLM 裁决作证据的注入是不安全的"。
10. **裁决可能被诱导**（v0.1 的 prompt 先给出"代码违反了这条需求"）。v0.2 测盲裁决。
11. **容差和求解间隙的选择影响授权结果**（1e-4 不通过，1e-3 通过）。审稿人可能认为容差是为通过而调的。应对：在开发集上按事先写好的规则选（取能通过审计的最小值），并报告敏感性。
12. **交付错误率目标是事先定的吗？** v0.1 没有事先声明，v0.2 要求事先声明。v0.1 的结果应当作探索性结果报告。

### 9.3 理论

13. spec-first 研究计划审查留下 7 条 MEDIUM 问题（B12–B18；审查记录在本地任务目录，未纳入仓库）：
    - B12：误拒的定义没有包含 blocked，但接受规则会拒绝 blocked 的决策；
    - B13：主论点"静默错误多数是漏掉需求后得到的松弛"证据不足，事先定好的检验 H1-P3 结果不确定（全部样本 64/113，F1–F4 42/70）；
    - B14：circular_sub 的失败归因于参考值过时，但数据分不清这和另一种原因（A6）；
    - B15：P6(e) 适用的四条规则在 F1–F4 上没有可检验的样本；
    - B16：P6 要求独立同分布，而 168 个决策中 126 个来自 GEPA A0，是被选择过的；
    - B17：部分合并统计混入了 F5–F8 样本，没有单列 F1–F4；
    - B18：P10 推论 2 漏了"向提问者澄清"这条信息来源。
14. **108/108 不能称为不可行证书精度**，只能称为 better 信号精度；有保证的是"数据集参考、τ ≥ 1e-2 下 F1–F4 68/68"。零 LLM 审计 P3 已经重解了 F1–F4 的 100 个参考值（全部证到最优、间隙 0；95 个与数据集参考一致，5 个 circular_sub 过时），可以据此更新口径。
15. **"OPTIMAL (TL) 不给出下界"这句话不对**：限时求解也可能有有效对偶界；准确说法是"只有 incumbent、没有记录对偶界时，无法构造可用的参考下界"。
16. **T3（交付风险分解）和 T5（修复方向引理）还没写**，写出来后需要检查是否只是平凡结论。

### 9.4 实验

17. **只有 1 个模型、1 个种子。** 这是最可能被直接拒稿的理由。
18. **测试集太少，而且 IndustryOR 开发时用过。** mamo 是唯一干净的测试集。
19. **和 SOTA 不能直接比。** 公开版本只覆盖了一部分；ORBench v3 没有已发表结果。
20. **ReLoop 和 OPT-Kraken 没跑。** 审稿人一定会要求。OPT-Kraken 的代码是否公开、能否在我们的设置下复现，**还不确定**。
21. **CodeT 式对照与多数投票完全相同**（M30），说明我们的 CodeT 实现可能有问题，或者在这个任务上 IR 检查当测试没有区分力。需要先查清楚，否则对照不公平。
22. **零成本 API 修补只给了 S3。** 如果对照组没有同样的兼容层，S3 的部分优势来自修补，而不是方法本身（M18：LogiOR 首轮 35 → 48）。
23. **mamo 上 23 题全部无答案**，可能是数据格式或题面的系统性问题。零 LLM 审计 P2 在查；如果是数据问题，要从评测中剔除或单独报告。
24. **事后反事实分析不能代替真实重跑。** 交付门对比、组件拆解都是在已存答案上重新计分。改变修复路线后会生成不同的答案，这部分只有重跑才能回答。
25. **成本对比**：S3 平均 2.2–2.3 次调用，但抽取调用很贵；和 CodeT 式比时，应同时给调用次数、token 和求解时间。

### 9.5 数据和伦理

26. **witness 的历史问题**：它一次性按全部 190 题写成；C-LABOR 用 F8 参考值校准；以前相对 ReLoop 的领先来自运行时 witness 反馈。论文方法已不使用 witness，但如果论文引用早期结果，必须说明。
27. **F5–F8 的暴露**：90 题中 24 题在 slice48 中暴露过，报告 66 题干净子集，两者冲突时以干净子集为准。
28. **ORBench 是用户整理的未发表数据**，引用和发布方式需要和数据作者确认。

### 9.6 投稿时机

29. ICML 截稿通常在 1 月下旬（以官网为准），离现在约两个月。要补齐多模型、多种子、ReLoop/OPT-Kraken 基线、v0.2 和至少一部分外环实验，时间很紧。NeurIPS（通常 5 月截稿）更现实。**建议等 v0.2 和 W1 结果出来再定。**

## 附录 B：v0.1 中一道题的完整路径（摘要）

LogiOR `prob_068`（最小化采购成本，参考值 80740.217）：
- IR 通道直接解出 80740.217（正确）。
- 代码通道首轮崩溃（`ub=m.infinity`），修复后得到 80300（错，花费集中度约束线性化写错，约束被放松）。
- 交叉检查：代码更松；代码解违反 IR 的 `spend_concentration`；IR 最优解在代码模型中可行；差分测试认为 `spend_concentration` 有争议，另有一条 `demand_satisfaction` 的误报（IR 写 "="、代码写 "≥"，在最优解上等价）。

- 在冻结版 C1 中，注入已关闭，这道题最终给出 80300（错）。

这道题同时说明了三件事：交叉检查能准确定位遗漏；按方向的注入是有价值的；差分测试需要处理等价写法的误报。
