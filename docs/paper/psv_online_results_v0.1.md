# F14 — 预求解验证器在线对照实验结果（v0.1）

日期：2026-11-02
状态：终稿（B 臂 5 分片全部完成，322 条环内记录）
数据：`runs/m1_presolve/`(B 臂）、`runs/m1_feedback/`(A 臂）、
`runs/m1_presolve/online_comparison.md`（由 `scripts/psv_online_analysis.py` 生成）

## 1. 目的

验证「预求解验证器」（需求台账 + 确定性 diff 静态闸门，设计见
`pre_solve_verifier_design_v0.1.md`，离线评测见 `psv_offline_results_v0.1.md`）
在在线闭环中的可测量收益：

> 把闸门放进「生成 → 校验 → 求解 → witness 重判 → 修复」回路后，相比只有
> 事后 witness 反馈的基线，真成功率、求解预算、残余错误结构如何变化？

## 2. 实验设计

- 数据集：RetailOpt-190(190 个零售供应链优化场景，f1–f8 难度家族）,on 模式
  （`reasoning_effort=medium`）计入主表。
- 模型：Qwen3_8-27B（内网服务）。
- Arm A（基线，F12 Route-B)：生成 → 直接求解 → witness 重判 → 失败则把 witness
  违例反馈给 LLM 修复，最多 3 轮。
- Arm B（本工作）：生成 → 静态闸门（台账 diff)→ block 则不求解、直接以缺口清单
  反馈修复；pass 才求解并走 witness 重判，最多 3 轮。
- 配对单元：(scenario, on) 共 190 cell；两臂共享同一 round-1 pilot 生成，差异只
  来自回路机制。
- 预算口径：环内（round ≥ 2)LLM 修复调用、闸门核查、执行尝试与墙钟；
  round-1 两臂共有，不计。

## 3. 主表

| arm | n | 真成功 | 成功率 |
|---|---|---|---|
| A（仅事后反馈） | 190 | 84 | 44.2% |
| B（+预求解闸门） | 190 | **87** | **45.8%** |

配对翻转：**B 独有成功 14 个，A 独有成功 11 个**（净 +3;McNemar 意义上不显著，
但方向为正）。名单见 `runs/m1_presolve/online_comparison.md`。

## 4. 预算对比（环内，on 模式，177 个进入回路的 cell)

| 指标 | A | B | 变化 |
|---|---|---|---|
| 环内记录（修复轮） | 318 | 322 | ≈持平 |
| 实际求解（exec ok) | 249 | 184 | **-26.1%** |
| LLM 修复耗时 | 19001s | 17378s | -8.5% |
| 执行墙钟（含崩溃） | 17370s | 14546s | **-16.3%** |
| 闸门核查开销 | 0 | 365 次 / 6191s | 新增 |

诚实结论：闸门自身核查花 6191s(LLM 调用），超过了执行侧省下的 2824s——
**本轮闸门的收益不在总墙钟预算，而在反馈质量与成功率**（见 §5/§6)。
（注：闸门 17s/次 的核查可通过缓存台账、缩短 prompt 大幅压缩，留作后续工程优化。)

## 5. 关键机制发现

1. **闸门的拦截集中在回路入口（round-1 代码）而非环内**:135 个 cell 是因闸门
   拦截 round-1 代码而进入修复（failure_in=presolve)，环内修复代码再被拦截仅
   **1 次**。与离线 F13 一致：幻影/结构遗漏集中在初生生成分布；一旦拿到确定性
   缺口反馈，模型很少再犯同类错误。
2. **闸门反馈比 witness 反馈更具可操作性**:B 独有的 14 个成功 cell 中，
   **12 个的首次修复由闸门缺口清单触发**（而非 witness 违例），其中 6 个一轮
   即修复成功（如 `retail_f4_demand_surge_v3`、`retail_f7_hub_and_spoke_v2`、
   `retail_f8_labor_constraint_v4`)。
3. **残余结构迁移符合设计预期**:witness_infeasible 75→50(-33%);
   crash 18→37(+106%)——闸门把「注定被 witness 判死的解」前置消化，瓶颈转移
   到代码健壮性（harness 工程问题，与验证器正交）。
4. 幻影拦截（离线 87.5–100% 召回）在线转化为「更少无效求解 + 更好的首轮修复
   信号」，而不是直接的在线 block 计数。

## 6. 定性案例

- `retail_f1_base_v0`(B 独有成功）:r2 以闸门缺口清单修复（in=presolve)，修复
  代码崩溃（crash);r3 以崩溃栈修复 → 求解成功、witness feasible、目标值 match。
  A 臂同 cell 未成功。
- `retail_f8_labor_constraint_v4`(B 独有成功）:r2 闸门反馈一轮即修复，exec ok /
  witness feasible / match，单轮闭环。
- smoke 案例 `retail_f1_52_weeks_v0`（设计阶段验证）:round-1 幻影解（C-INIT 隐藏
  约定违例），闸门反馈一次即修复为 witness 可行，零额外求解。

## 7. 局限

1. 净成功率 +1.6pp(配对 +14/-11)，样本量下统计功效有限；需更多 seed 或更难题
   分布确认。
2. 闸门核查自身成本（6191s）未压缩，本轮总墙钟两臂基本持平。
3. 闸门对成功样本的离线通过率 84.6%(11/13),fail-open 设计缓解误拦风险。
4. 单模型（Qwen3_8-27B）、单数据集家族，外推需谨慎。
5. witness 仅覆盖 witness-only 规则族（如 C-INIT 隐藏约定）；「语义一致但数值
   次优」类错误不在两臂任一验证器射程内。

## 8. 结论

在 RetailOpt-190 × Qwen3_8-27B 的配对对照中，预求解验证器带来：

- 真成功率 44.2% → 45.8%(+3 cell，配对翻转 +14/-11);
- 求解调用 -26.1%、执行墙钟 -16.3%（但闸门核查开销抵消总墙钟收益）;
- witness_infeasible 残余 -33%，错误结构从「语义/建模层」转向「代码健壮性层」;
- 机制证据：离线高召回的幻影拦截，在线主要转化为**更高质量的首轮修复信号**
  （12/14 B 独有成功由闸门反馈触发），而非在线 block 计数。

满足完成标准③中「错误提前拦截率（135 个入口拦截）、真成功率提升、求解预算
节省」三项可测量收益。下一步方向：压缩闸门核查成本、把闸门台账沉淀为跨题
memory（自进化）、并扩展到更难题分布验证统计显著性。
