## 3. 三个关键案例

### 3.1 `prob_021`：执行错误重复，随后开发补丁修复

原始三臂均在两轮内重复 `sense="max"`，没有改成 `"maximize"`。v0.3.1 在执行反馈中明确给出 PySCIPOpt 写法后，scoped IR 一轮修复，最终独立目标值为 81000，业务正确。

这是一次 **execution recovery**，不是语义违规恢复。

### 3.2 `prob_104`：生成器与检查器共享语义偏差

初始模型把并行时间写成：

```python
0.5 * FertilizerUnits + 1.5 * SeedsUnits
```

scoped IR 也写成同样的加法，因此三者都接受初始解，没有触发修复。独立参考语义应为：

```python
max(0.5 * FertilizerUnits, 1.5 * SeedsUnits)
```

这说明 scoped IR 无法自动保证业务语义正确；当作者与生成器共享错误假设时，限定 JSON 也会漏检。

### 3.3 `prob_229`：文本修复把正确解修坏

初始独立目标值 181，文本修复后变成 633，且独立公式重算应为 50，形成 `harmed_win`。 scoped IR 没有修改它，保持正确。说明最终独立评分与候选版本保护不可缺少。

## 4. 当前结论

1. 完整技术链路已经存在并可运行，但原始协议要求的“至少一个真正语义违规被修复”**尚未达到**。
2. scoped IR 没有产生 `harmed_win`，且 token 最低，但这不等于语义审计已经可靠。
3. 固定制品上的高检出不能外推到自然生成；检查器可能和生成器共享同一个错误业务假设。
4. 独立专家公式与公开目标值仍必须保留为外部裁判，不能用 scoped IR 自证成功。
5. 执行错误的显式 API 反馈有效；语义错误需要更强的机制覆盖、独立反例和修复控制，而不是继续增加提示长度。

## 5. Makespan 语义类型补丁

v0.3.2 将 `makespan` 作为独立语义类型，规定多个必需活动的完成时间若可并行，应使用 `max` 而非 `add`。该试验仅对 `prob_104` 运行，结果为：

- scoped IR 仍将目标写成 `0.5*F + 1.5*S`，未使用 `max`；
- 初始错误解继续被接受，`accepted_round=0`、`repair_calls=0`；
- 独立评分保持不正确，没有语义恢复。

按补丁协议已停止，不再继续提示词迭代。原始目标因此只能结题为：**端到端技术链路与一次执行恢复已实现，但目标语义修复机制未验证成功。**
