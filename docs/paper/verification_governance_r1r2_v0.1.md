# 验证知识治理：R1 出处授权与 R2 层级接受（v0.1）

## 摘要

本文档形式化项目研究讨论中提出的两条规则：**按出处授予否决权（R1）**与**按层级接受修复（R2）**。研究对象不是如何再生成一个更强的答案，而是：当生成器和验证器都在进化时，谁有资格否决一个答案，以及什么样的修复可以被接受。

R1 将“提出检查”与“获得否决权”分离，要求检查同时具备语义出处和可信行为审计。R2 将修复目标分层，要求低层修复不得随意改变已授权高层检查的结论。两者共同构成一个有出处、有审计、有生命周期、有接受约束的验证知识治理框架。

当前实现是最小原型。静态幻影已有实验证据，R1/R2 的有效性与跨域通用性仍需通过后续对照实验验证。

## 1. 研究背景：弱代理成功不等于真实正确

在优化建模、代码生成和 Text-to-SQL 中，系统通常使用低成本代理信号指导生成和进化：

- OR：求解目标值与参考值匹配，或最小化问题中目标值更低；
- 代码：原始测试通过；
- Text-to-SQL：在单个数据库上的执行结果与 gold 一致。

这些信号与真实正确性并不等价：

- SCIP optimal 只表示对候选代码写下的模型求到了最优解，不保证该模型符合原始业务问题；
- 原始测试通过可能只是因为测试覆盖不足；
- 单数据库执行一致不保证 SQL 在其他数据库状态上语义等价。

定义：

```text
true_correct   = 弱代理通过，且独立强检查通过
phantom_proxy  = 弱代理通过，但独立强检查失败
proxy_unknown  = 弱代理通过，但强检查无法确定
```

因此：

```text
proxy_match = true_correct + phantom_proxy + proxy_unknown
```

UNKNOWN 不能当作安全。静态幻影的存在说明代理与真实正确性会分离；自进化是否会进一步放大这种分离，是当前 A0 基线要检验的问题。

## 2. 治理问题：生成器和验证器都可能出错

一种自然修正方案是让系统从失败中学习检查器，再用检查器指导修复。但这会产生两个新的风险。

### 2.1 未经验证的检查获得否决权

检查器可能：

- 把某个题族的局部惯例误当成普适规则；
- 语义判断正确，但代码实现错误；
- 只拟合少量样例；
- 对正常解产生误报；
- 将 UNKNOWN 当成通过；
- 在进化中被修改得越来越宽松。

因此，“存在一条检查”不能等价于“这条检查可以否决答案”。

### 2.2 修复改变高层语义，造成修坏或洗白

一次针对执行或弱代理的修复可能：

- 提高代理分，却破坏原本正确的业务约束；
- 修复一个错误，同时引入另一个错误；
- 通过修改、绕过或削弱检查，使高层结果从 fail 变成 pass；
- 多轮修复后逐渐偏离原始业务需求。

因此，不能只看修复前后的弱代理分，还必须约束高层检查结果如何变化。

## 3. R1：按出处授予否决权

### 3.1 核心原则

```text
提出检查 ≠ 获得否决权
```

所有新检查从 `hint_only` 开始。只有同时具备语义出处和可信行为证据的检查，才能晋升为 `veto_enabled`。

### 3.2 检查资产

每个检查资产包含：

- `check_id`；
- 所属层级；
- 检查函数及代码哈希；
- 父版本；
- 题面或已验证惯例出处；
- 可信审计样本与重放结果；
- 当前状态；
- 退休原因。

当前状态机：

```text
注册为 hint_only
       ↓
出处校验 + 可信审计
       ↓
veto_enabled 或 rejected
       ↓
出现可靠反例时 retired
       ↓
最终评测阶段 frozen，禁止写入
```

冻结前可以注册新版本，但必须保留父版本并重新审计；不能通过原地修改检查代码绕过历史。

### 3.3 两类独立证据

**语义出处**回答“这条检查依据什么业务规则”。允许：

- 题面中的逐字依据；
- 经过独立验证、带不可变注册哈希的惯例资产。

**行为证据**回答“这条检查的实现是否真的识别错误”。要求在可信审计集上精确重放，并区分：

- clean：独立确认应当通过的样本；
- wrong：独立确认应当失败的样本；
- UNKNOWN：无法判断，不能计入通过。

当前原型门槛为：

- 至少 3 个 clean 和 3 个 wrong；
- clean 误报为 0；
- precision ≥ 1.0；
- detection ≥ 0.6；
- UNKNOWN = 0。

这些数值只是原型的最低授权门槛，不是普适最优阈值，也不构成对检查器全局正确性的证明。

### 3.4 为什么出处和审计必须同时存在

只有出处，可能出现“题面理解正确、代码实现错误”。只有审计，可能出现“拟合少量样本、缺乏业务依据”。

例如，候选检查为：

```text
sales + sub_out - sub_in + lost == demand
```

它需要同时满足：

1. 能定位到题面需求守恒定义；
2. 对独立参考解不误报；
3. 对打破需求平衡的独立反例能够检出；
4. 审计过程中没有 UNKNOWN。

满足后才允许否决候选。

### 3.5 跨族迁移的含义

R1 不支持把旧域否决权直接复制到新域。更合理的迁移过程是：

```text
旧域检查模板
→ 新域 hint_only
→ 新域字段绑定与题面出处核验
→ 新域 clean/wrong 审计
→ 本地 veto_enabled
```

因此，可迁移的是检查模式、反例和适用条件；具体否决权需要在新域重新获得。

## 4. R2：按层级接受修复

### 4.1 检查层级

当前使用三层：

```text
L0：弱代理
    目标值匹配、原始测试、单数据库执行结果

L1：执行与输出契约
    能否执行、是否存在解、输出是否完整可读

L2：独立语义检查
    RetailOpt Witness、EvalPlus、Text-to-SQL test suite
```

层级不是绝对真理排序，而是修复责任划分。更高层检查也必须先通过 R1 才能获得否决权。

### 4.2 层级接受规则

设一次修复的目标层为 `t`，修复前后的逐题检查结果分别为 `before` 和 `after`。

对所有满足以下条件的检查 `c`：

```text
c.status == veto_enabled
c.level > t
```

必须同时满足：

1. 修复前后都存在该检查的 verdict；
2. `before[c] == after[c]`。

缺失结果按拒绝处理。

形式化表示：

```text
repair_allowed(t, before, after)
⇔ 对所有已授权且 level > t 的检查，修复前后 verdict 完全一致
```

相同层或更低层的结果可以变化。若确实需要改变某个高层结果，必须显式以该高层为修复目标，而不是在弱代理修复中附带改变它。

### 4.3 为什么 fail → pass 也不能随意接受

高层 `fail → pass` 可能是真实修复，也可能是检查洗白。若当前修复只针对执行或弱代理，这种变化缺乏明确责任归属，因此不能直接接受。

例如：

| 修复情况 | 决策 | 原因 |
|---|---|---|
| 弱代理提高，L2 `pass → fail` | 拒绝 | 修坏原本正确的高层语义 |
| 执行修复，L2 `fail → pass`，但没有 L2 修复目标 | 拒绝 | 无法区分真实修复与洗白 |
| 显式修复 L2，目标 L2 `fail → pass`，其他高层不变 | 允许进入后续审核 | 修复目标与证据一致 |
| 任意修复导致高层 verdict 缺失 | 拒绝 | 无法证明高层语义未改变 |

### 4.4 与最终门禁的区别

原始 R2 约束的是**修复过程中高层 verdict 是否改变**。

当前原型还实现了一个附加条件：

```text
final_accept(after)
⇔ 所有已授权检查在最终输出上均为 pass
```

UNKNOWN 不是 pass，没有已授权检查也不能自称完成治理接受。

这个最终门禁是额外的过滤机制，不能和原始 R2 混为一谈。正式消融应分别评估：

- 只有 R2 高层不变约束；
- 只有最终门禁；
- 两者同时启用。

否则无法判断收益究竟来自修复过程约束，还是来自简单过滤。

## 5. R1 与 R2 的互补关系

只有 R1 时，虽然知道当前答案错误，但仍可能接受修坏其他约束或不明示目标的高层翻转。

只有 R2 时，只能保护已授权检查；如果检查本身错误，可能错杀正确解或保护错误惯例。

组合后的含义是：

```text
R1：谁有资格检查和否决
R2：答案怎样变化才允许被接受
```

二者共同构成：

> 有依据的检查 + 有约束的修复。

## 6. 与 memory 和 DAG 的关系

### 6.1 Memory：验证知识资产库

R1 的注册表可以成为一种验证 memory，保存：

- 检查模板；
- 题面或惯例出处；
- 代码哈希和父版本；
- clean/wrong 反例；
- 适用条件；
- 授权状态和退休历史。

它与原始文本经验 memory 的区别是：每条记忆都有证据、生命周期和使用权限。跨域迁移时，记忆可以作为提示，但不能未经本地审计直接获得否决权。

### 6.2 DAG：修复路径编排

DAG 可以记录：

- 父子候选；
- 每次修复针对的层级；
- 高层检查结果如何变化；
- 哪个分支引入幻影；
- 哪些正确结果被保留。

R2 决定 DAG 中哪些修复边可以保留，R1 决定节点上的检查是否具有否决权。

DAG 是组织方式，不保证修复有效；没有可靠检查和接受规则时，它可能只是增加搜索成本。

## 7. 当前实现与原型的边界

核心实现：`ora_agent/verification_governance.py`。

已经实现：

- 检查资产生命周期；
- 来源结构校验；
- 可信样本重放；
- 检查代码哈希和审计记录；
- 冻结与退休；
- 高层 verdict 逐项比较；
- 缺失和 UNKNOWN 拒绝；
- 最终授权检查门禁；
- GEPA 候选接受插件。

当前尚未证明或尚未完整实现：

1. 多数候选检查仍是预写的确定性检查函数，只是自动触发和晋升，不是 LLM 自由生成全新检查器。
2. 3+3 审计不足以证明跨族可靠性，且部分样本与参考模型共享假设。
3. 部分惯例出处仍是简化登记，正式实验需要真实不可变 registry 和独立验证证据。
4. 当前 GEPA 适配主要把候选视为低层代理改进，完整的高层修复路由尚未实现，R2 可能过严。
5. 当前最终门禁与原始 R2 尚未完成独立消融。
6. 未编码的业务语义仍可能漏检；UNKNOWN 不会被误判为安全，但检查覆盖不足仍会导致假阴性。

因此，当前不能把该原型描述成“已经实现通用、自进化、跨域 Witness”。

## 8. 实验设计

### 8.1 A0：先验证 motivation

A0 使用官方 GEPA/AlphaOPT 和弱代理，不加入 R1/R2，强检查只落盘、不进入基线反馈。

逐代记录：

- 弱代理成功率；
- 独立强检查真正确率；
- `phantom_proxy / proxy_match`；
- 可执行率；
- UNKNOWN 和生成失败；
- 成本。

若代理分没有提高，只能报告静态代理高估，不能声称进化放大。

### 8.2 固定候选池：测规则的直接效果

让 A0/A1/A2/A3 审查完全相同的原始生成结果：

```text
A0：原始弱代理接受逻辑
A1：加入 R1
A2：加入 R2
A3：同时加入 R1 和 R2
```

使用逐题 paired win/loss 和 McNemar 检验，避免不同采样轨迹造成混杂。

### 8.3 在线进化：测规则对后续学习的影响

让规则参与候选接受，固定初始候选、模型、数据、官方评测预算和真实 LLM 成本口径，使用多个随机种子。

额外消融：

- `hint_only` 与未审计直接否决；
- 只有高层不变约束与只有最终门禁；
- 固定低层修复与显式高层修复路由；
- 原始文本 memory 与带出处和审计的验证 memory。

## 9. 评价指标与证伪条件

### R1 需要报告

- 检查授权率和拒绝率；
- 授权检查在独立审计上的误报率；
- 幻影拦截率；
- 正确解错杀率；
- UNKNOWN 与未覆盖比例；
- 反例导致的退休情况。

### R2 需要报告

- 高层 `pass → fail` 数量；
- 非目标高层 `fail → pass` 数量；
- 原本正确 win 的保留率；
- 合理高层修复被阻止的比例；
- 最终无输出比例；
- 额外 LLM 调用和 token 成本。

### 不能算作成功的结果

- 幻影下降只是因为所有候选都被拒绝；
- 可执行率或真正确率大幅下降却被隐藏；
- 通过修改检查器使高层通过率提高；
- 只报告代理优化选出的最好候选；
- 将 UNKNOWN、服务失败或未覆盖语义当成正确；
- 用同一套进化中的检查同时充当接受依据和唯一最终真值，形成循环验证。

## 10. 后续可扩展方向

R1/R2 不直接决定预算或候选生成策略，但可以为控制器提供结构化状态：

- 相同代码哈希重复出现时停止重复修复；
- 多次出现高层翻转时换父候选，而不是继续烧预算；
- 某类高层错误需要显式高层修复时进行路由；
- 检查覆盖不足时返回 UNKNOWN/人工审计，而不是继续自称安全；
- 根据修复成功率、检查覆盖和成本决定继续、换候选或停止。

这些属于后续控制器与 DAG 编排设计，不应提前计入当前两条规则的实验收益。

## 11. 研究结论的边界

R1/R2 的潜在研究贡献不是两个固定检查器，也不是简单的拒绝策略，而是：**在非参数自进化过程中，验证知识也必须进化，但只有经过出处验证和独立审计的知识才能获得否决权，并且修复接受必须受到高层语义约束。**

它们是否有效，最终取决于：

- 是否减少新增幻影；
- 是否保留真实 win 和有效修复；
- 是否避免过度拒绝；
- 是否在 GEPA、AlphaOPT 等不同方法中成立；
- 是否在 RetailOpt、EvalPlus、Text-to-SQL 等不同领域中复现；
- 是否能清楚报告验证覆盖、成本和负结果。

在这些实验完成前，R1/R2 是一个有明确动机、可执行、可证伪的机制设计，而不是已经验证有效的最终答案。
