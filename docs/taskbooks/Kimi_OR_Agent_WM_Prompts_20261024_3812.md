# Kimi 交接 Prompt：通用 OR Agent 与跨任务动作后果预测

版本：2026-10-24

使用方法：第一次把本文件交给 Kimi，执行「Prompt A」。B、C、D 用于后续迭代，不要求第一轮全部完成。本文是一份系统研发任务书，包含设计约束、首轮实施范围和研究接口，并非已经验证有效的系统方案。

## 交接前的架构判断

目标表述：

> 通用 OR agent 是系统主体。跨任务的动作后果预测是候选核心研究能力。问题内部及求解器内部的 world model 是可以进一步展开的专业能力。

模型与系统角色：

| 对象 | 当前建议 | 后续可能 |
| --- | --- | --- |
| Kimi 3.1 coding agent | 开发、调试与维护工程，执行本任务书 | 单独评估其作为运行时 actor 或 teacher 的效果 |
| 现有 Qwen 27B 服务 | 主运行时 OR agent，读取任务、生成模型或代码、调用工具、修改求解方案 | 根据真实失败选择 SFT、RL、蒸馏或其他学习 |
| 动作后果预测能力 | 先实现可替换接口与真实预测记录，可调用现有 LLM | 基于真实轨迹训练模型，或归纳可执行模型 |
| PEARL-4B | 参考 solver-in-the-loop 训练与交互机制，模型可作为后续小模型对照 | 部署成本比较、专用角色、蒸馏或策略学习 |
| PlanB&B | 保留为某些 MILP 后端的专业能力候选 | 独立验证适用性、接入成本和实际总耗时收益 |
| 旧 GNN/MLP | 复用有价值的工程与实验经验，重新判断表示和接口是否兼容 | 有结构化任务和充分数据时再选择相应架构 |

上述选择不要求沿用 MIS、SC 数据集、固定 formulation、greedy 初始解、LNS 外循环，也不要求一开始采用多 agent 或联合训练。保留旧工程和结果，在独立工作区或分支实施新系统。

本文中的 Qwen 27B 指用户现有服务。公开存在 Qwen/Qwen3.8-27B，但现有部署可能采用服务别名。必须从实际配置和最小请求确认 model_id、provider、base_url 和能力，不依据聊天中的“qwen3/8-27b”自行拼接模型名。Kimi 的 CLI、订阅认证和 API 服务也不能默认互换。

## Prompt A：设计、实现并跑通第一版系统

你是本项目的 coding agent，承担系统架构、工程实现、实验执行和可复现报告。请自主推进到第一个真实端到端结果，随后完成首轮小规模开发实验。常规实现选择由你判断，不要只提交方案或列出待办。

### A1. 目标与需要检验的假设

构建能够处理异构自然语言优化任务的 OR agent：

1. 读取自然语言要求、文件和配置，理解目标、约束与数据含义。
2. 自主选择数学规划、CP、直接算法、启发式、分解或混合方案。
3. 生成或修改 formulation、可执行代码及求解流程。
4. 调用实际程序和求解器，获得解、日志与运行结果。
5. 根据原始任务检查产物，继续诊断、修复或改善。
6. 按任务协议交付模型说明、代码、日志和决策文件。

候选研究假设：显式预测计算动作的后果，能改善 agent 的问题解决能力。它的收益必须通过真实任务和实际成本检验。

系统应在不启用预测模块时独立完成上述工作。预测模块的缺陷不应阻止基础 OR agent 继续求解。

### A2. 实际环境检查与组件复用

先进行一次简短、以实现决策为目的的 fit-gap 检查，随后开始工程：

- 阅读本地项目说明、已有模型调用封装、可用 solver、容器和相关依赖。检查实际 GPU 与显存，历史上提过的两块 A800 仅作为线索。
- 核实用户现有 Qwen 服务的实际标识、请求格式、上下文配置、输出限制，以及工具调用或命令输出解析方式。
- 使用现有凭据，不输出密钥，不把凭据写入代码、轨迹或报告。报告模型与端点配置时只保留必要的非敏感信息。
- 对照现有组件：Harbor、ORAgentBench 自带适配器与 skills、mini-swe-agent，以及本地已经可用的 agent runner。
- 若需要程序种群和演化管理，再快速比较 OpenEvolve、ShinkaEvolve、PathWise。第一轮不要求集成任何一个演化框架。

给出精简 fit-gap 表：组件、准备复用的部分、缺口、适配成本、决定。记录实际版本或 commit。不要为了阅读所有论文而推迟首次运行。

优先复用 agent 循环、模型客户端、容器执行、任务 runner 和产物管理。定制工作集中在 OR 语义与验证、状态/动作记录、预测接口和研究实验。不要同时重建通用 harness、记忆数据库、技能平台和多 agent 框架。

### A3. 系统结构与设计自由

默认从一个主要运行时 OR agent 出发。它可以在一次任务内多次规划、编码、执行和修改。若引入 reviewer 或其他角色，需要说明其具体职责和成本，不按预设“三个 agent”复制角色。

最低需要的能力边界：

- Task adapter：只向 agent 暴露协议允许的任务说明、数据、工具和反馈。
- Runtime actor：依据可见历史提出具体行动。
- Workspace/artifacts：保存版本化的任务状态、模型、代码、解与日志。
- Execution：真实运行工具、程序和求解器。
- Verification：根据可见需求进行独立检查，并与离线官方评价区分。
- Prediction：对拟执行动作给出事前预测，可切换关闭、旁路记录和参与决策。
- Experience export：保存可用于后续训练及离线评估的真实轨迹。

这些是功能接口，不要求实现七个独立服务或七个模型。可以直接适配成熟 runner，通过少量 hooks 完成。

允许 agent 提出开放的代码和 formulation 修改。结构化工具接口用于可靠执行，动作标签用于统计分析；两者不应把算法创新限制成一个固定的小菜单。

### A4. 候选方案、状态与动作的表示

统一对象是“可执行求解方案”。它可以是 solver 程序、原生算法、分解流程或混合方案，包含相关表示、实现、后端、控制参数及预算。

不要把 formulation 和代码设为互斥路线。允许原生算法给 solver 提供初始解，也允许代码继续改善 solver 产生的解。后端不支持续跑或状态迁移时，如实重新启动并计入开销。

状态表示必须适应变长任务与异构方法。先保留准确的文件、代码版本、工具历史和结构化摘要；不要先规定一个旧实验维度的数值向量。摘要和后续预测均应能追溯到来源。

可见状态至少覆盖：当前任务解释、数据特征、方案版本、执行历史、已有解及验证证据、未知问题、剩余资源。没有可用 objective、bound 或解时返回缺失值和状态原因。

动作应尽量具体到可执行对象：明确的程序修改、工具参数、实验计划、求解调用或诊断命令。若 actor 只提出“换一种模型”等意图，先将其落实成具体候选，再预测这个候选的执行后果。研究抽象意图预测时另立实验。

已知的文本修改和文件变化可以精确处理。预测学习重点放在尚未执行且有价值的未知后果。

### A5. 预测模块的接口与诚实命名

预测输入：当前可见历史、具体动作或候选、运行条件与拟使用预算。

可选预测输出：

- 程序能否正常运行，以及可能的失败类型。
- 预算内获得有效解或改善的可能性。
- 可能出现的验证结果和诊断观察。
- 执行后的关键状态及后续可采取的动作。
- 消耗及不确定性。

输出应支持“未知、当前证据不足”。概率和区间必须经经验检验，不把 LLM 自评直接称为已校准。

初版可以使用现有 Qwen 作为预测后端，也可比较另一种现成实现。区分：

- 事前 LLM 预测基线：尚未通过本项目的轨迹训练。
- 表现预测器：主要输出候选分数或最终收益。
- 过程模型候选：预测动作引起的观察与状态变化，可以支撑后续行动。
- 已训练模型：确有参数更新或可执行模型归纳、真实数据来源和独立评估。

不要仅因为类名叫 WorldModel，就宣称完成了世界模型研究。第一轮允许只完成基线与数据接口。

### A6. 验证与任务含义

对比候选前，确认它们是否解决同一版本的任务。特别区分等价改写、搜索内部的松弛/限制/近似，以及业务要求的变更。

可以广泛探索内部松弛和修复，但最终业务解依据原任务核验。不同表示解码到共同的业务决策后，按原目标比较。不能直接比较含义不同的目标、未对齐的 bound 或来自错误模型的“最优解”。

使用约束追溯、独立解检查、小实例精确对照、差分测试或反例等有用手段。LLM 语义检查属于证据之一。小实例一致和某个 LLM 判断通过，都不能自动证明所有实例等价。

在静态任务中，缺失业务事实不能由 agent 自编用户回答。记录有依据的解释与未解决假设。只有任务协议提供交互时才使用 user/user-agent 接口。

### A7. 基准与数据隔离

第一主线采用 ORAgentBench，优先复用其环境、runner、skills 和产物协议。当前官方工程使用 Harbor，实际安装与运行命令以固定版本 README 为准。

CO-Bench 用于后续隔离算法设计与迭代能力。其问题说明和求解函数接口，与多文件端到端业务任务不同。第一轮完成 ORAgentBench 即可；保留薄适配接口，不要求同时完整实现两个基准。

开发执行只暴露公开任务材料和协议允许的观察。隐藏 evaluator、reference/oracle、参考解和隐藏指标不进入 actor 或 predictor 的上下文。

区分以下信息：

- online_observation：运行中允许 agent 看到的执行和自检结果。
- offline_evaluation：最终提交固定后，外部 evaluator 给出的分数。
- development_feedback：协议允许用于开发版本选择的汇总反馈。

未明确允许的隐藏评分不能变成在线修复工具。held-out 结果不得反馈给模型继续修改同一个被评估候选。训练数据的使用范围按实际协议记录。

预先固定开发集和研究用 held-out，避免同源实例或任务变体跨集合泄漏。官方全量分数与我们自定义研究划分分别报告。首轮小样本只用于工程与可行性判断。

### A8. 轨迹、版本与事前预测

复用现有轨迹格式，补上确有必要的字段。至少能够关联：

- task_id、任务类型、split、run_id、state_id 和父版本。
- actor/predictor 的模型标识、版本、请求配置和实验条件。
- 具体动作、修改摘要、相关产物路径或 hash。
- 预测输入范围、预测内容、预测产生时间和动作 hash。
- 实际工具调用、运行结果、执行后的状态和验证来源。
- 资源消耗、失败/超时/截断信息，以及 offline_evaluation 的独立记录。

预测必须在观察其结果前写入并冻结。禁止从结果倒填预测。必要时采用独立进程或消息边界确保没有未来反馈混入。

超时、没有解、执行错误、验证不通过、已证明不可行等状态分开保存。没有观察到改善，不等于证明不存在改善。不要为了得到整齐训练表而把缺失值填成伪造 objective。

保留成功与失败轨迹，不只导出最后赢家。无需收集私有推理链；可使用允许存储的决策摘要、工具消息、代码和结果。

### A9. 首轮执行范围

第一轮按下面的工作包推进；这些是实施顺序，不是要求反复等待人工审批的门槛。

1. 完成精简 fit-gap、模型/工具调用冒烟和实际架构选择。
2. 复用 runner，实现一个不启用预测模块的完整 OR agent 基线。
3. 选 2–3 个不同类型开发任务跑通实际产物、执行与评价，直接修复阻塞。
4. 将开发 pilot 扩到约 6 个跨类型任务；记录选择依据，首轮不跑全量大矩阵。
5. 在部分有价值的具体动作上接入旁路预测，冻结后真实执行并对照。
6. 在可复制状态上采集少量不同动作的真实分叉结果，形成第一份动作条件预测样本。
7. 若接口已经可靠且预算允许，做一个小规模“预测参与决策”试验；否则交付已完成的真实能力，并说明下一步最有价值的实现。

默认使用用户现有模型服务，不把微调、大规模数据生成或多 agent 当作首次运行的依赖。设计必须支持参数学习，第一轮不要求在尚无数据时盲目训练。

任务内优先遵循官方资源限制，并统一额外 token、时间和调用上限。若本地没有试验上限，配置一个保守的小规模开发默认值并明确记录，避免无限重试和自动扩展到全量任务。

本轮要获得实际可审阅结果。即使预测效果不好，也继续改进基础 agent 与数据采集；不要把一次预测失败变成整个工程停止的理由。

### A10. 研究对照与成本

第一轮至少交付强且完整的无预测基线，以及同状态、同动作的旁路预测证据。后续根据资源开展：

- 同一 actor 直接推理与实际尝试。
- 使用相同历史的反思/笔记对照。
- 候选表现排序。
- 使用动作后果预测进行选择或短程规划。

所有在线比较使用相同基础模型、工具权限、公开信息和总资源限制。无预测基线可以把节省的资源用于正常求解。需要分离“多了计算”和“预测内容有效”时，额外设置匹配计算的对照。

预测准确性评估时，冻结状态与候选集合，执行多个候选取得真实结果。端到端策略比较时，允许轨迹自然分叉，不能要求各臂执行相同行动。

用于离线构造反事实标签的额外试验，不能偷渡成在线免费 oracle。记录训练/数据构造成本、在线成本和可能的跨任务摊销。

快照不等于能复制求解器内存。无法恢复的状态从相同版本和条件重跑，并记录启动开销。随机种子只是复现条件之一。

报告字段按任务可得性选择：产物有效率、可行率、原目标质量、首个可行解耗时、最终质量/改善轨迹、官方通过率，以及全部 LLM 与求解开销。预测侧检查错误事件、候选排序、不同动作的效果差异，以及概率/区间的经验可靠性。

不发明“必须提升 X% 才能继续”等阈值。小样本报告不确定性和失败案例，改进决策依据证据与实际效用。

### A11. 第一轮交付

第一份交付包含以下真实完成项：

- 可运行代码、实际配置模板、依赖与复用来源。
- 简明架构图和关键设计决策，包括旧组件保留/改造/暂缓的理由。
- 至少一次真实端到端任务运行的模型说明、代码、日志与决策产物。
- 开发 pilot 运行清单、预算、各任务结果，以及失败归因。
- 事前预测及真实观察的成对记录；未完成的部分明确标记。
- 可复跑命令、版本、数据划分和原始结果路径。
- 下一轮直接改善求解能力的改动，以及预测/训练研究需要补充的证据。

可以做接口的基本单元验证，但 mock API、模拟日志和手工答案只能验证软件，不计入真实求解或预测效果。

若外部依赖、凭据或权限确实阻塞，明确指出缺失项，完成不依赖它的实现与本地验证。不要把未运行标记成通过。

现在开始：检查现有工程与资源，做简短复用决策，然后实现并运行上述第一轮。不要停在文献综述和框架图。

## Prompt B：把首轮闭环推进成有竞争力的 OR agent

请读取上一轮实际代码、运行记录和产物，不从聊天摘要重建工程。

本轮目标：提高端到端求解能力，并得到可信的动作后果预测评估。请优先处理实际造成失败或低质量的主要瓶颈，避免通过继续增加角色和基础设施代替改进求解。

请完成：

1. 从真实任务中区分需求误解、数据处理、formulation、实现错误、可行解构造、解质量改善与预算使用问题。为最高影响项给出具体证据。
2. 实现一组有实质差异的改进，允许更换算法、表示、后端或混合流程，保持原任务评价一致。
3. 保留强无预测基线，让它获得完整工具和预算。将预测参与决策作为独立实验条件。
4. 选择若干可复制的中间状态，冻结可见信息与候选，记录预测后执行多个候选。保留预测不看好的动作样本，减少选择偏差。
5. 检查模型是否真的区分同状态不同动作，还是只预测相近的平均未来。
6. 比较已有真实观察、候选打分与状态/观察预测分别提供了什么信息。若要做多步规划，说明中间预测状态怎样支持下一步动作，并实测误差与开销。
7. 修复最影响结论的实现或评估问题，再用固定任务、预算和版本复跑。无需因为预测不占优就停止基础 agent 的改进。

交付新的真实结果、代码差异、成本和下一轮选择。报告不能只写“动作敏感性不足”等诊断，要给出已经采取的改动及其效果。若预测仍无净收益，保留有用的 OR agent 和数据，并明确尚未得到支持的假设。

## Prompt C：为预测与策略选择可执行的参数学习路线

请基于现有真实轨迹和工程选择学习方案，不默认沿用 PEARL-4B、GNN/MLP，也不默认一定要微调 27B。

目标：检验真实经验能否改善跨任务的动作后果预测，并进一步帮助 OR agent。请先明确要学习的能力和数据，再选择网络或程序形态。

需要比较的候选路线：

- 现成 LLM 的事前预测，作为参照。
- 同一 LLM 加检索到的历史证据，检验非参数适应。

训练设计要求：

1. 输入只包含动作前可见的信息和具体动作；目标来自真实执行。确定的文件修改与未知执行后果分开处理。
2. 训练、验证和测试按任务及同源变体隔离；held-out 的结果不能进入学习和检索。
3. 成功、错误、超时、无解和反例都要有正确语义。连续目标仅在有有效解及可比定义时使用。
4. LLM 自己生成的解释和 imagined rollout 不直接当作真实环境标签。
5. 区分严格事前预测、见过后续经验的回顾性分析，以及用于选择候选的最终性能评价。
6. 参数更新与非参数证据复用尽量分开比较。记录更新数据、训练开销和旧任务保留。
7. 在可行的小规模条件下执行一次真实学习试验。资源不足时给出明确缺口及经过验证的导出/训练入口，不宣称训练已完成。

先改善预测能力，再检验它能否转化为决策收益。联合更新 actor 与 predictor 可以后续研究；第一项实验中同时修改所有部件会使收益难以归因。
