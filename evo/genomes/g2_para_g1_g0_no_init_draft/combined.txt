[KNOWN PITFALLS — read before writing code]
These are environment/API conventions for this PySCIPOpt harness, distilled
from past failures. Follow them strictly:

1. The prelude already loads `data` from data.json. NEVER reassign `data`
   (e.g. `data = None` or `data = {}` kills every subsequent data[...] access),
   and read data ONLY from data.json — opening any other filename
   (scenario.json, <name>.json, ...) raises FileNotFoundError.
2. m.setObjective: the sense must be the string "minimize" or "maximize"
   (never "min"/"max"), passed as a keyword: m.setObjective(expr, "minimize").
3. setObjective takes ONE expression, not a Python list — sum terms with
   quicksum([...]) first, and never pass a list indirectly via a variable
   (obj = [...]; m.setObjective(obj) also fails).
4. quicksum is a module-level function: from pyscipopt import quicksum.
   m.quicksum(...) and m.sum(...) do not exist.
5. Build comparisons ONLY inside m.addCons(...); never use <=, >=, == on
   expressions in if/assert/bool contexts (it raises TypeError, not a
   constraint).
6. m.infinity is a METHOD: call m.infinity() — passing it uncalled as ub/lb
   raises TypeError.
7. m.setParam only with real SCIP parameter names (e.g. limits/time,
   limits/gap, presolving/maxrounds); never invent parameter names.
8. The code must parse as Python 3: watch indentation and bracket balance,
   especially in long quicksum expressions.
9. PySCIPOpt has NO gurobipy-style attributes: no .ObjVal/.Status/.X/.Pi/.ub/
   .lb/.getLb()/.getUb(). Use m.getObjVal(), m.getStatus(), m.getVal(v),
   m.chgVarLb(v, x) / m.chgVarUb(v, x) instead.

[MODELING PROCEDURE — follow this order BEFORE writing code]
1. UNDERSTAND: one short paragraph — objective and its sense; the decision
   variables; every constraint; and which data fields activate which
   mechanisms (check moq/pack_size/budget_per_period/waste_limit_pct/
   sub_edges/trans_edges/return_rate/labor values in the data schema — a
   zero/null/empty field means that mechanism is INACTIVE for this instance).
2. FORMALIZE: list each decision variable with its domain — CONTINUOUS,
   INTEGER, or BINARY; decide from physical meaning (units of product may be
   continuous; counts of trucks/workers/setups are INTEGER; yes-no decisions
   are BINARY). Then write every constraint as a one-line math statement with
   its index sets, and the objective as a sum of ALL cost/revenue terms
   mentioned in the problem.
3. VERIFY against the problem text: every constraint from the text has an
   addCons, every cost term appears in the objective, every data key you use
   exists in the DATA SCHEMA. Fix any gap, then output the code.


[SEMANTIC CONVENTIONS — demand, substitution, and the solution dump]
The following rules define the precise semantic standards against which your generated solution.json will be validated. Adhere to these specifications strictly; do not apply alternative interpretations or conventions.
1. Definition of demand: For any product p, location l, and week t, the demand value is calculated strictly as demand_curve[p][t-1] multiplied by demand_share[l]. Do not alter, rescale, or recompute this value using any other source or method.
2. Demand balance requires a strict equality constraint for every (p,l,t) triple, rather than an inequality for coverage:
       own_sales[p,l,t] + sub_received[p,l,t] + lost[p,l,t] == demand[p,l,t]
   Exceeding demand in sales is physically impossible because customers must exist to purchase goods. If you model demand as a ">=" coverage inequality, the optimizer will artificially inflate sales to capture non-existent revenue.
3. The direction of substitution must align precisely with the dump contract:
   sub["pf|pt|l|t"] represents the quantity of demand for product pf that is satisfied by substitute product pt.
   Your model must enforce the following consequences:
   - For the primary product (pf): own_sales[pf] plus the sum of all substitutions sub[pf,pt] plus lost[pf] must equal the total demand for pf.
   - For the substitute product (pt): The total units shipped of pt, which includes its own sales plus the sum of all substitutions sub[pf,pt], must be deducted from pt's inventory (accounted for in pt's outflow or inventory balance). A single physical unit cannot fulfill two separate demands—allocating the same units to the demand of both products constitutes double counting.
4. lost[p,l,t] denotes the unmet demand specifically for that (p,l,t) combination and must be nonnegative.
   Should the problem instance prohibit lost sales, this restriction must be implemented by setting lost == 0 within the balance equation—do not remove the variable or allow it to take negative values.
5. Completeness of the dump: solution.json must document every possible index combination for (p,l,t[,r]) regarding sales, I, lost, Q, W, sub, and X, even when the value is zero. If a key is absent, the verifier treats it as 0, which will silently invalidate the balance checks for all other products, locations, or weeks that are connected to it.
6. Big-M discipline: Any linking constraints must employ a tight big-M value (for example, the production capacity specific to that product and week). Avoid using large constants such as 1e20 in any context, as they introduce phantom flow into the model.
7. Explicitly constrain initial inventory variables to zero for all SKUs, DCs, and weeks. Additionally, confirm that demand balance constraints aggregate only actual sales and substitutions, ensuring that any residual initial stock terms are excluded from the sum.
