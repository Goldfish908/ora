## CRITICAL: Building the Objective Expression

**NEVER use `variable.obj` to access objective coefficients.** Variable objects in PySCIPOpt 6.3.0 do NOT have an `.obj` attribute. Attempting `v.obj` will raise `AttributeError: 'pyscipopt.scip.Variable' object has no attribute 'obj'`.

Instead, you MUST:
1. Store all objective coefficients in your own Python dictionaries/data structures when reading data.
2. Build the objective expression explicitly by multiplying your stored coefficients by the variable objects.

**Correct pattern:**
```python
# Store coefficients in your own dict
obj_coeff = {}
for (p, o) in pairs:
    obj_coeff[(p, o)] = revenue[o] - cost[p, o]  # your computed coefficient

# Create variables (you CAN set obj= in addVar, but it's optional)
x = {}
for (p, o) in pairs:
    x[(p, o)] = model.addVar(name=f"x_{p}_{o}", vtype="I", lb=0, ub=100, obj=obj_coeff[(p, o)])

# Build objective EXPLICITLY using your stored coefficients:
obj_expr = quicksum([obj_coeff[(p, o)] * x[(p, o)] for (p, o) in pairs])
model.setObjective(obj_expr, sense="maximize")
```

**WRONG pattern (will crash):**
```python
# DO NOT do this:
obj_expr = quicksum([v.obj for v in x.values()])  # AttributeError!
# DO NOT do this:
obj_expr = quicksum([v for v in model.getVars() if v.obj != 0.0])  # AttributeError!
```

If you set `obj=` in `addVar`, the coefficients ARE set on the model internally, but you CANNOT read them back via `v.obj`. You must track them yourself.

## CRITICAL: Defensive Dictionary Lookups

When building large models with many lookup dictionaries (lane data, mode data, eligibility tables, etc.), ALWAYS use defensive access patterns to avoid KeyError crashes:

```python
# BAD: will crash if key missing
cost = modeCostMult[(p, d, mode)]

# GOOD: use .get() with a default, or check existence first
cost = modeCostMult.get((p, d, mode), 1.0)  # default 1.0 if not found
# OR
if (p, d, mode) not in modeCostMult:
    continue  # skip this combination
```

When iterating over combinations derived from one table and looking them up in another, verify the key exists first. A common source of KeyError is when a lane exists in the routes table but has no corresponding entry in the transport modes table (or vice versa). Always guard with:
```python
modes = pin_modes.get((p, d), [])
for mode in modes:
    if (p, d, mode) not in modeCostMult:
        continue
    # safe to use modeCostMult[(p, d, mode)]
```

## CRITICAL: Model Tractability and Scale Management

**This is the #1 cause of failure in large problems.** Before building the full MIP, estimate the number of variables and constraints:

- **Small MIP** (< 500 vars, < 2000 cons): Solve directly with SCIP. This is typical for problems with ≤ 5 entities × ≤ 10 periods.
- **Medium MIP** (500–5000 vars): Solve directly but consider:
  - Tighter variable bounds (use problem-specific UBs, not infinity)
  - Fixing obvious binary decisions (e.g., if a plant must be open due to minimum uptime from prior months)
  - Eliminating redundant constraints
  - Setting SCIP parameters for better presolving: `model.setParam("presolving/maxrounds", 10)`
- **Large MIP** (> 5000 vars, especially > 1000 binaries): The model will likely NOT solve to optimality within 5 minutes. In this case:
  - **Decompose**: Solve subproblems (e.g., by time period, by plant, by product) and combine.
  - **Heuristic warm start**: Build a greedy feasible solution first, then use SCIP to improve.
  - **Fix obvious decisions**: If a binary must be 1 (e.g., plant open due to min uptime), fix it and remove the variable.
  - **Reduce binary count**: If transport mode binaries are unnecessary (e.g., each lane has exactly one mode), eliminate them entirely.
  - **Relax and round**: Solve LP relaxation, round integer variables, repair feasibility.
  - **Always produce a feasible solution**: Even if SCIP times out, extract the best incumbent or build a heuristic solution.

**Common large-model mistakes:**
- Creating a binary variable for every (month, lane, mode) when each lane has only one mode — this multiplies binary count unnecessarily.
- Creating shipment variables for every (month, plant, DC, product, mode) when mode is fixed per lane — use (month, plant, DC, product) only.
- Not fixing plant-open variables that are forced by initial conditions and minimum uptime.
- Adding redundant constraints (e.g., both a capacity constraint AND a mode-capacity constraint when they are identical).

## Transport Mode Handling

When the problem includes transport modes:
- Each lane (route) may have one or more modes available.
- If a lane has exactly ONE mode, you do NOT need a binary for mode selection. Just use that mode's cost multiplier and CO2 multiplier directly in the objective and constraints.
- If a lane has MULTIPLE modes, you need mode-selection binaries, but be careful:
  - The mode minimum (min_mode_tons_if_used) applies per mode, not per lane.
  - The lane capacity is the sum across modes.
  - Cost = base_cost × mode_cost_multiplier (do NOT divide by number of modes).
  - CO2 = base_co2 × mode_co2_multiplier (do NOT divide by number of modes).
- The `monthly_mode_capacity.csv` gives aggregate capacity per mode per month across ALL lanes. This is a global constraint.
- The `material_contract_tiers.csv` may impose minimums on specific material purchases that interact with mode selection.

**Correct cost calculation for a shipment on a lane with one mode:**
```python
# If lane (p, dc) has mode RAIL with cost_multiplier 0.96:
effective_cost = base_transport_cost * 0.96  # NOT base_transport_cost / 1
effective_co2 = base_co2 * 0.72
```

## Common Pitfalls to Avoid

1. **`v.obj` does not exist**: As stated above, never access `.obj` on Variable objects. Always track coefficients in your own data structures.

2. **KeyError on dictionary lookups**: When cross-referencing data from multiple CSV files (e.g., routes table vs. transport modes table), always verify keys exist before accessing. Use `.get()` with defaults or `if key in dict` guards. A lane in `plant_to_dc_routes.csv` may not have a corresponding entry in `transport_modes.csv`, or column name mismatches can cause silent key differences.

3. **Tuple unpacking errors**: When iterating over dictionaries with multi-element tuple keys, always verify the number of elements matches your unpacking pattern. For example, if keys are `(p, dc, pd, m, mode)` (5 elements), do NOT unpack as `(p, dc, pd, mode)` (4 elements).

4. **setObjective signature**: The second positional parameter is `sense`, not a name. If you want to name the objective, there is no name parameter in this API version. Just use `model.setObjective(expr, sense='maximize')`.

5. **Integer vs continuous variables**: Production quantities that must be integer parts/packs use `vtype='I'`. Setup/activation decisions use `vtype='B'`. Continuous quantities (tons, kg) use `vtype='C'` (default).

6. **Rounding solution values**: After solving, round integer variables to nearest integer with `int(round(model.getVal(var)))`. For continuous variables, use `f'{val:.8f}'` format.

7. **Solution file must ALWAYS exist**: The evaluator checks for the solution file. If the solver fails or times out, still attempt to write a best-effort solution file. Wrap the solve in try/except and always write the output file. **A missing solution file means a score of zero regardless of code quality.**

8. **Validation before writing**: After extracting the solution, validate all constraints are satisfied within tolerance before writing the file. Print validation results.

9. **Eligibility filtering**: Only create variables for feasible combinations (e.g., only eligible printer-material pairs, only approved lot-order pairs, only qualified plant-product-month combinations). This dramatically reduces model size.

10. **Binary linking constraints**: For setup/activation variables that gate production, use `x <= bigM * y` where bigM is a tight upper bound on x (e.g., the maximum possible production, not an arbitrary large number).

11. **Weighted average constraints**: When a constraint requires a weighted average to meet a threshold (e.g., average SoH >= minimum), linearize by moving the threshold to the left: `sum(weight_i * value_i * x_i) >= threshold * sum(weight_i * x_i)`.

16. **Do NOT divide costs by number of modes**: If a lane has one mode with cost_multiplier 0.96, the effective cost is `base_cost * 0.96`. Do NOT write `base_cost * 0.96 / num_modes` — this is only correct if you are summing over modes, which you should not do when there is a single mode.

17. **Model.md must be substantive**: The evaluator may check for a complete mathematical model. Include: sets, indices, parameters (with data source), decision variables (with types), objective function (full expression), and all constraints (numbered). Do not write "placeholder" or a one-line summary.

18. **Startup logic for plants/facilities**: When modeling plant open/close with startup:
    - `start[t] >= open[t] - open[t-1]` (startup implies transition)
    - `start[t] <= open[t]` (can only start if open)
    - `open[t] - start[t] >= open[t-1]` (if was open and not starting, stays open) — this is redundant with the first two, so use only two constraints.
    - For the first period: `open[1] - start[1] >= initial_open` (if initially open, must stay open or start)
    - Minimum uptime: if `start[t]=1`, then `open[t+k] >= 1` for k=0..min_uptime-1.

19. **BOM (Bill of Materials) balance**: When production consumes raw materials, the constraint is:
    `material_purchased >= sum over products of (BOM_coeff * production)`
    This is an inequality (>=), not equality, because you can purchase more than needed (though the optimizer won't in a cost-minimization).

20. **Inventory balance with initial inventory**: For the first period: `inv[1] = initial_inv + inbound - outbound`. For subsequent periods: `inv[t] = inv[t-1] + inbound - outbound`. If initial inventory is zero (as specified in config), the first period simplifies to `inv[1] = inbound - outbound`.

21. **Service level constraints**: 
    - Monthly shortage fraction: `shortage[t] <= max_fraction * demand[t]` for each month.
    - Horizon fill rate: `sum_t shortage[t] <= (1 - min_fill_rate) * sum_t demand[t]`.
    - These are separate constraints and BOTH must be included.

22. **Sourcing share rules**: "At least X% of delivered volume must come from approved DCs" means:
    `sum(shipped from approved DCs) >= X * sum(all shipped volume)`
    This is relative to delivered volume, NOT total demand. Shortage is excluded from the denominator.

23. **Split delivery rules**: "At least Y% of that month's demand must be shipped from DC Z" means:
    `ship[DC_Z, customer, product, month] >= Y * demand[customer, product, month]`
    Multiple split rules for the same customer-product-month must ALL be satisfied simultaneously.

24. **CO2 budget**: Sum of (material_co2 * purchases + process_co2 * production + transport_co2 * shipments) <= monthly_budget. Apply mode CO2 multipliers to transport emissions.

25. **Route-product exclusions**: If a product is excluded from a route, simply do NOT create shipment variables for that (route, product) combination. This is cleaner than adding a constraint that forces the variable to zero.

26. **Product-specific inventory caps**: These are ADDITIONAL constraints on top of the DC's aggregate storage capacity. Both must be enforced:
    - `inv[month, dc, product] <= product_specific_cap` (from inventory_caps.csv)
    - `sum over products of inv[month, dc, product] <= dc_storage_capacity` (from distribution_centers.csv)

27. **Safety stock**: `inv[month, dc, product] >= safety_stock[month, dc, product]`. This is a lower bound on ending inventory.

28. **Take-or-pay material contracts**: If plant is open, `material_purchase >= contract_minimum`. If plant is closed, no minimum. Model as: `material_purchase >= min_tons * open[month, plant]`.

29. **Campaign (plant-product) rules**:
    - Qualification: only create production variables for months >= qualified_from_month.
    - Min batch: `total_production >= min_batch * setup_binary` (if min_batch > 0).
    - Max output: `total_production <= max_output * setup_binary`.
    - Setup cost: add `setup_cost * setup_binary` to objective.
    - Setup only if plant open: `setup_binary <= open[month, plant]`.

30. **Output row types**: Different problems require different row types in the solution CSV. Read the problem statement and template carefully. Common types include:
    - `setup` / `product_setup`: binary activation decisions
    - `produce` / `regular_production` / `overtime_production`: production quantities
    - `ship_plant_dc` / `ship_dc_customer`: transportation flows (include mode_id)
    - `inventory`: ending inventory levels
    - `shortage`: unmet demand
    - `build`: integer pack/part quantities
    - `procure` / `material_purchase`: raw material quantities
    Only include rows with positive values (or include zero rows if the schema allows).
