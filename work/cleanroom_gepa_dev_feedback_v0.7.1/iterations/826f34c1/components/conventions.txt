## CRITICAL: Building the Objective Expression

**NEVER use `variable.obj` to reference objective coefficients.** The Variable object in PySCIPOpt 6.3.0 does NOT have an `.obj` attribute. Accessing it will raise `AttributeError: 'pyscipopt.scip.Variable' object has no attribute 'obj'`.

Instead, store all objective coefficients in your own Python dictionaries/lists when you compute them, then build the objective expression explicitly:

```python
# CORRECT approach:
obj_coeffs = {}  # store coefficients as you compute them
obj_coeffs[(p, o)] = revenue - cost1 - cost2  # example

# Build objective explicitly:
obj_expr = quicksum([
    obj_coeffs[key] * var_dict[key] for key in var_dict
])
model.setObjective(obj_expr, sense='maximize')

# WRONG approach (will crash):
# model.setObjective(quicksum(v.obj for v in var_dict.values()), sense='maximize')
```

You CAN pass `obj=coeff` to `addVar()` to set the coefficient on the variable internally, but you CANNOT later retrieve it via `var.obj`. The safest pattern is to:
1. Store coefficients in your own dictionaries.
2. Optionally pass them to `addVar(obj=...)` for SCIP's internal use.
3. Build the final objective expression explicitly from your stored coefficients and variable objects.

## Common Pitfalls to Avoid

1. **`variable.obj` does not exist**: Never write `v.obj` or `var.obj`. Store coefficients in your own data structures and build the objective expression explicitly using `quicksum([coeff * var for ...])`.

2. **Tuple unpacking errors**: When iterating over dictionaries with multi-element tuple keys, always verify the number of elements matches your unpacking pattern. For example, if keys are `(p, dc, pd, m, mode)` (5 elements), do NOT unpack as `(p, dc, pd, mode)` (4 elements).

3. **setObjective signature**: The second positional parameter is `sense`, not a name. If you want to name the objective, there is no name parameter in this API version. Just use `model.setObjective(expr, sense='maximize')`.

4. **Integer vs continuous variables**: Production quantities that must be integer parts/packs use `vtype='I'`. Setup/activation decisions use `vtype='B'`. Continuous quantities (tons, kg) use `vtype='C'` (default).

5. **Rounding solution values**: After solving, round integer variables to nearest integer with `int(round(model.getVal(var)))`. For continuous variables, use `f'{val:.8f}'` format.

6. **Solution file must exist**: The evaluator checks for the solution file. If the solver fails or times out, still attempt to write a best-effort solution file.

7. **Validation before writing**: After extracting the solution, validate all constraints are satisfied within tolerance before writing the file. Print validation results.

8. **Eligibility filtering**: Only create variables for feasible combinations (e.g., only eligible printer-material pairs, only approved lot-order pairs). This dramatically reduces model size.

9. **Binary linking constraints**: For setup/activation variables that gate production, use `x <= bigM * y` where bigM is a tight upper bound on x (e.g., the maximum possible production, not an arbitrary large number).

10. **Weighted average constraints**: When a constraint requires a weighted average to meet a threshold (e.g., average SoH >= minimum), linearize by moving the threshold to the left: `sum(weight_i * value_i * x_i) >= threshold * sum(weight_i * x_i)`.

11. **Cross-file data consistency**: When one file defines the set of entities (e.g., lanes) and another file provides parameters for those entities (e.g., transport modes per lane), always check that the parameter file has an entry before using it. Use `if key in dict:` or `dict.get(key, default)` patterns. If a lane exists in the routes file but has no mode entry in the modes file, either skip it or assign a default mode.

12. **Environment variable for time limit**:
```python
import os
time_limit = 300.0  # default 5 minutes
env_limit = os.environ.get("ORCLAW_SOLVE_TIME_LIMIT_SECONDS")
if env_limit is not None:
    try:
        time_limit = min(time_limit, float(env_limit))
    except ValueError:
        pass
model.setParam("limits/time", time_limit)
```

13. **Large models and time limits**: For large MIPs (hundreds of binary variables, thousands of continuous variables), the solver may not reach optimality within the time limit. In that case, the best incumbent found is still valid. Always check `model.getNSols() > 0` before extracting a solution, and write the best available solution even if the solver status is "timelimit" or "gap".

14. **Objective with both positive and negative coefficients**: When maximizing profit (revenue minus costs), some per-unit contributions may be negative (e.g., using an expensive printer for a low-margin order). This is fine — SCIP will naturally avoid negative-contribution assignments unless forced by minimum fill constraints. Do not artificially restrict variables to only positive-contribution pairs unless the problem explicitly forbids it.

15. **Output schema compliance**: Carefully read the required output schema in the problem statement. Column names, row types, and which fields to fill vs. leave blank must match exactly. For example, if the schema says "put the pack family in order_id and leave lot_id blank" for setup rows, do exactly that.
