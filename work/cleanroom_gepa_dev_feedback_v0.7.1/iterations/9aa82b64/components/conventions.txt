## CRITICAL PITFALLS (CAUSE RUNTIME CRASHES)

### Pitfall 1: Variable `.obj` attribute does NOT exist
In PySCIPOpt 6.3.0, `Variable` objects do NOT have an `.obj` attribute. You CANNOT do:
```python
# WRONG - will crash with AttributeError:
model.setObjective(quicksum(v.obj for v in model.getVars()), sense="minimize")
```
Instead, you MUST build the objective expression explicitly using the coefficient values you computed:
```python
# CORRECT - build objective from known coefficients:
obj_terms = []
for key, var in x_vars.items():
    obj_terms.append(coeff_dict[key] * var)
model.setObjective(quicksum(obj_terms), sense="maximize")
```
Or set coefficients via `addVar(obj=coeff)` AND also build the expression explicitly (do not rely on reading them back).

### Pitfall 2: Dictionary key structure mismatches
When building dictionaries with tuple keys, be EXTREMELY careful about nesting:
```python
# Building:
l = (r["from_id"], r["to_id"])  # l is a 2-tuple
modeCapLane[(l, r["mode_id"])] = value  # key is ((from, to), mode) - a 2-tuple where first element is a 2-tuple

# Later lookup:
modeCapLane[(p, d, mode)]  # WRONG! This is a 3-tuple (p, d, mode)
modeCapLane[((p, d), mode)]  # CORRECT! This matches ((from, to), mode)
```
Always verify that the key structure used for insertion matches the key structure used for lookup. When in doubt, use flat 3-tuples `(p, d, mode)` consistently for both insertion and lookup.

### Pitfall 3: Always write the solution file
Even if the solver fails, times out, or returns infeasible, you MUST write a solution file. Use a try/except around the solve and write a best-effort (possibly empty or heuristic) solution. The evaluator checks for file existence.

### Pitfall 4: Tuple unpacking with multi-element keys
When iterating over dictionaries with multi-element tuple keys, always verify the number of elements matches your unpacking pattern.

### Pitfall 5: Integer vs continuous variables
- Production quantities that must be integer parts/packs: `vtype='I'`
- Setup/activation decisions: `vtype='B'`
- Continuous quantities (tons, kg, hours): `vtype='C'` (default)

### Pitfall 6: Rounding solution values
After solving:
- Integer variables: `int(round(model.getVal(var)))`
- Continuous variables: `f'{val:.8f}'` format
- Binary variables: `int(round(model.getVal(var)))` then check `> 0.5`

## Modeling and Solving Strategy

Before running expensive solves, reason about the problem structure and choose an efficient approach. You may:
1. Use stronger mathematical formulations and more sophisticated modeling strategies tailored to the structure, special properties, and scale of the given problem instance.
2. Solve directly with SCIP when the model is tractable.
3. Design effective heuristic, local-search, repair, or rounding methods when exact optimization is too slow.
4. Combine heuristics with SCIP, for example by generating an initial feasible solution, fixing or relaxing selected variables, using warm starts if supported, or solving restricted subproblems.
5. Run short diagnostic solves to estimate difficulty, then refine the model and solution method.

Do not default to a naive formulation. Before coding, explicitly analyze whether the problem is better represented as an assignment model, network flow model, set partitioning model, time-indexed model, interval/order-based scheduling model, routing model, or decomposition-based model. Choose the formulation that is likely to give the strongest relaxation and fastest solution for the given instance size. Use preprocessing, dominance filtering, bound tightening, valid inequalities, symmetry breaking, and heuristic warm starts whenever applicable.

### For LARGE multi-period models (e.g., 4+ facilities × 3+ products × 6+ periods × 5+ DCs × 8+ customers):
- The model can have tens of thousands of variables and constraints. Be strategic:
  - Use tight upper bounds on all variables (derive from demand, capacity, etc.)
  - Eliminate variables that are provably zero (infeasible routes, unqualified products)
  - Consider whether the problem decomposes by product or by time
  - If the full MIP is too large, consider solving a relaxed version first, then fixing key decisions
  - Set appropriate SCIP parameters for large models (e.g., `presolving/rounding`, `separating/maxrounds`)
- The model may not solve to optimality within the time limit. In that case, ensure you have a good incumbent and write it.

### For SMALL models (e.g., <500 variables):
- Solve directly with SCIP; should reach optimality quickly.
- Focus on correct formulation and output schema.

Use the limited iteration budget wisely:
- First ensure feasibility and correct output schema.
- Then improve objective quality.
- Prefer targeted refinements over repeated full solves.
- Stop iterating when additional improvements are unlikely within the remaining time.
- Record every meaningful solve attempt and validation result in `/app/submissions/solve_log.md`.

The final submission should prioritize correctness, feasibility, and robust execution from scratch under the time limit.
