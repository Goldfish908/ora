## CRITICAL: Building the Objective Expression

**NEVER use `variable.obj` to access objective coefficients.** Variable objects in PySCIPOpt 6.3.0 do NOT have an `.obj` attribute. Attempting `v.obj` will raise `AttributeError: 'pyscipopt.scip.Variable' object has no attribute 'obj'`.

Instead, you MUST:
1. Store all objective coefficients in your own Python dictionaries/data structures when reading data.
2. Build the objective expression explicitly by multiplying your stored coefficients by the variable objects.

**Correct pattern:**
```python
# Store coefficients in your own dict
obj_coeff = {}
for (p, o) in pairs:
    obj_coeff[(p, o)] = revenue[o] - cost[p, o]  # your computed coefficient

# Create variables (you CAN set obj= in addVar, but it's optional)
x = {}
for (p, o) in pairs:
    x[(p, o)] = model.addVar(name=f"x_{p}_{o}", vtype="I", lb=0, ub=100, obj=obj_coeff[(p, o)])

# Build objective EXPLICITLY using your stored coefficients:
obj_expr = quicksum([obj_coeff[(p, o)] * x[(p, o)] for (p, o) in pairs])
model.setObjective(obj_expr, sense="maximize")
```

**WRONG pattern (will crash):**
```python
# DO NOT do this:
obj_expr = quicksum([v.obj for v in x.values()])  # AttributeError!
# DO NOT do this:
obj_expr = quicksum([v for v in model.getVars() if v.obj != 0.0])  # AttributeError!
```

If you set `obj=` in `addVar`, the coefficients ARE set on the model internally, but you CANNOT read them back via `v.obj`. You must track them yourself.

## CRITICAL: Defensive Dictionary Lookups

When building large models with many lookup dictionaries (lane data, mode data, eligibility tables, etc.), ALWAYS use defensive access patterns to avoid KeyError crashes:

```python
# BAD: will crash if key missing
cost = modeCostMult[(p, d, mode)]

# GOOD: use .get() with a default, or check existence first
cost = modeCostMult.get((p, d, mode), 1.0)  # default 1.0 if not found
# OR
if (p, d, mode) not in modeCostMult:
    continue  # skip this combination
```

When iterating over combinations derived from one table and looking them up in another, verify the key exists first. A common source of KeyError is when a lane exists in the routes table but has no corresponding entry in the transport modes table (or vice versa). Always guard with:
```python
modes = pin_modes.get((p, d), [])
for mode in modes:
    if (p, d, mode) not in modeCostMult:
        continue
    # safe to use modeCostMult[(p, d, mode)]
```

## Common Pitfalls to Avoid

1. **`v.obj` does not exist**: As stated above, never access `.obj` on Variable objects. Always track coefficients in your own data structures.

2. **KeyError on dictionary lookups**: When cross-referencing data from multiple CSV files (e.g., routes table vs. transport modes table), always verify keys exist before accessing. Use `.get()` with defaults or `if key in dict` guards. A lane in `plant_to_dc_routes.csv` may not have a corresponding entry in `transport_modes.csv`, or column name mismatches can cause silent key differences.

3. **Tuple unpacking errors**: When iterating over dictionaries with multi-element tuple keys, always verify the number of elements matches your unpacking pattern. For example, if keys are `(p, dc, pd, m, mode)` (5 elements), do NOT unpack as `(p, dc, pd, mode)` (4 elements).

4. **setObjective signature**: The second positional parameter is `sense`, not a name. If you want to name the objective, there is no name parameter in this API version. Just use `model.setObjective(expr, sense='maximize')`.

5. **Integer vs continuous variables**: Production quantities that must be integer parts/packs use `vtype='I'`. Setup/activation decisions use `vtype='B'`. Continuous quantities (tons, kg) use `vtype='C'` (default).

6. **Rounding solution values**: After solving, round integer variables to nearest integer with `int(round(model.getVal(var)))`. For continuous variables, use `f'{val:.8f}'` format.

7. **Solution file must exist**: The evaluator checks for the solution file. If the solver fails or times out, still attempt to write a best-effort solution file. Wrap the solve in try/except and always write the output file.

8. **Validation before writing**: After extracting the solution, validate all constraints are satisfied within tolerance before writing the file. Print validation results.

9. **Eligibility filtering**: Only create variables for feasible combinations (e.g., only eligible printer-material pairs, only approved lot-order pairs). This dramatically reduces model size.

10. **Binary linking constraints**: For setup/activation variables that gate production, use `x <= bigM * y` where bigM is a tight upper bound on x (e.g., the maximum possible production, not an arbitrary large number).

11. **Weighted average constraints**: When a constraint requires a weighted average to meet a threshold (e.g., average SoH >= minimum), linearize by moving the threshold to the left: `sum(weight_i * value_i * x_i) >= threshold * sum(weight_i * x_i)`.

12. **Environment variable for time limit**:
```python
import os
time_limit = 300.0  # default 5 minutes
env_limit = os.environ.get("ORCLAW_SOLVE_TIME_LIMIT_SECONDS")
if env_limit is not None:
    try:
        time_limit = min(time_limit, float(env_limit))

model.setParam("limits/time", time_limit)
```

13. **Large model tractability**: For problems with many binary variables (e.g., 4 plants × 3 products × 6 months × multiple lanes × modes), the MIP can become very large. Consider:
    - Reducing the number of binary variables by fixing obvious decisions
    - Using tighter bounds on continuous variables
    - Setting appropriate SCIP parameters for presolving and heuristics
    - If the model is too large, consider a decomposition approach or a heuristic that produces a feasible solution

14. **Solution schema compliance**: The output CSV must match the exact schema specified in the problem. Check column names, row types, and which fields should be blank. The evaluator will reject files with wrong schemas.
