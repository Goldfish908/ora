## Modeling Strategy

Before coding, analyze the problem structure:

- **Small MIPs (≤500 binary vars):** Solve directly with SCIP.
- **Medium MIPs (500–5000 binary vars):** Use strong formulations, valid inequalities, and SCIP's presolve. Consider fixing obvious variables before solving.
- **Large MIPs (>5000 binary vars):** Consider decomposition (Benders, Lagrangian), heuristic warm starts, or solving a relaxed problem first then repairing. You may combine: generate a feasible solution heuristically, feed it as a start solution to SCIP, then let SCIP improve.

**Formulation tips:**
- Prefer formulations with tighter LP relaxations (e.g., network flow over set partitioning when applicable).
- Use Big-M carefully — set M as tight as possible.
- Add symmetry-breaking constraints when the problem has symmetric structures.
- For scheduling problems, time-indexed formulations with linking constraints (z = sum of covering y's) are standard.
- For production-distribution, consider whether a BOM-based flow formulation or a campaign-based formulation is tighter.
- Preprocess: remove dominated options, tighten bounds, identify forced decisions.

**Heuristic strategies (when exact solve is too slow):**
- Greedy assignment by cost/profit ratio.
- Local search / tabu search on the assignment structure.
- Solve LP relaxation, then round with repair.
- Fix a subset of binary variables, solve the remainder, iterate.
- Column generation for set-partitioning formulations.

## Common Pitfalls to Avoid

- **Wrong import:** `pysis` does not exist. Use `pyscipopt`.
- **Missing `setMaximize()`:** If the problem is a maximization and you forget this, SCIP minimizes the (positive) objective, giving the worst solution.
- **Objective sign errors:** In a maximization, setup costs should have negative coefficients (or you negate the whole objective for minimization).
- **Big-M too large:** Use the tightest valid upper bound to avoid numerical issues.
- **Missing constraints:** Re-read the problem statement for every business rule, exception table, and service-level requirement. Each one maps to a constraint.
- **Integer vs. continuous:** Production counts, part counts, and setup decisions are typically integer/binary. Flow quantities (tons, kWh) are continuous.
- **Feasibility tolerance:** Use the tolerance from `config.json` (typically 1e-5) in validation checks.
- **Output schema:** Match the exact column names and row types specified. Omit zero-valued rows unless the schema says otherwise.
- **Data edge cases:** Some (entity, period) combinations may not appear in data files. Use `.get()` with defaults or check membership before accessing.
