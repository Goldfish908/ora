# IndustryOR 语义绑定与完整内环开发协议 v0.1

## 边界

这是**开发回放**，不是新的 held-out 结果。初始候选来自 `work/industryor_full_qwen_v0.1` 已保存的 Qwen3.8-27B 响应，保持代码不变。历史全集结果已经可见，因此后续改动不得称为未见测试集提升或通用跨族结论。

第一阶段只重放 ID 4/8/20，检验三个不同问题：单复数变量名、带索引的变量名、名称不同且存在真实指示约束缺口。后续扩展必须保留所有失败，不按结果筛题。

## 绑定与 Pre-solve

内网 Qwen3.8-27B 仅接收题面、候选代码、独立业务变量 schema 和已导出的变量名/类型，不接收 `en_answer`、参考目标值或参考解。模型只返回 `solver_name → semantic_name` 及候选代码中的逐字证据。

Pre-solve 仅检查：

- 必需语义变量是否被唯一覆盖；
- 可直接识别的求解器变量声明域是否兼容；
- 导出 AST 结构与别名冲突；
- 已有导出中是否存在所称 solver_name。

`ready` 只允许进入执行，不代表业务正确。循环生成变量等无法在求解前完全证明的绑定必须经运行时导出核验。约束和业务目标仍由独立 post-solve scorer 判定。

## 重绑定与模型修复的区别

仅重绑定使用 `instrument_code(code, aliases)` 改变导出名称，不改变模型内部变量、目标或约束。修复前后目标值应保持一致，独立 scorer 重新检查业务语义。

如果重绑定后暴露真实业务违例，必须把该违例作为后续局部修复证据，重新求解和审计。不能仅修改变量名把 UNKNOWN 或错误解包装成正确解。

## 制品与后续对照

每题保存初始代码、绑定 prompt、原始 LLM 响应、逐字证据、gate、插桩代码、执行 stdout/stderr、solution、独立评分与成本。缓存不计入新调用。

后续 DAG 对照使用同一初始候选和绑定。单线与多分支必须使用相同独立 scorer、预算与接受规则；不以 `en_answer` 选择分支，不开启跨题 memory/RSI。只有独立业务证据支持的改善才称为语义恢复。

## 三臂内环对照

- `bind_only`：只做语义绑定和导出，不做模型修复。
- `single_line`：优先局部修复，未通过时从当前局部候选重生成，每题最多一次重生成。
- `branch_dag`：从同一根候选派生局部修复和重生成两个分支。开发模式 `stop_on_accept=False`，即使一个分支已通过也评估另一分支，以检查替代路径和额外成本。该模式不是生产预算最优策略。

局部修复目前仅覆盖有独立证据的 ID 9/19/20/21。ID 48 的缺失角色进入重生成反馈，不手工伪造通过。三臂共享绑定、根执行和相同 messages 的重生成缓存；共享缓存不重复计外部调用。

候选接受要求 SCIP optimal、独立业务审计通过和 binding 有效。多个候选可接受时按 LLM 调用、SCIP 次数、深度、节点 ID 依次选择，不使用参考答案或裸目标值。无可接受候选时保留根候选并明确标记未接受。局部修复、重生成、重复、失败和 UNKNOWN 均保留在 DAG 中。

## 重生成后的再绑定

候选代码变化后不得盲目复用旧变量别名。先依据新代码的 AST 删除不存在的 solver_name，并对代码中实际声明的规范语义变量使用 identity binding。若覆盖仍不足，可新增一次绑定 LLM 调用；绑定与重生成分别计入预算。运行时再次核对导出和独立业务评分，不能因绑定 `ready` 就接受业务上错误的模型。

v0.2 对照复用 v0.1 的原始重生成 messages/response，并逐文件记录 SHA256。这样只改变再绑定连接，不重新采样初始模型或修复模型。复用响应的逻辑调用与实际新增调用分别报告；不能把缓存回放写成零总成本。

绑定完整不等于业务正确。例如目标规划偏差目标与业务利润目标不一致时，即使所有变量均可审计且变量约束可行，也必须因业务目标不一致拒绝接受，不临时修改 scorer 或注入参考答案。
